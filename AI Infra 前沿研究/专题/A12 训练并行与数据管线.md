# A12 训练并行与数据管线：并行策略开始由"数据长度分布"和"优化器"决定

> [!abstract] 一句话
> 教科书式的做法是按模型大小静态选 DP/TP/PP/EP/CP 的组合。2026 年的一手材料显示，这个选择越来越被两个"recipe 变量"左右：**序列长度分布的长尾**（让固定的 CP/SP 度数浪费算力）和**优化器**（Muon 需要完整矩阵，改变了分片方式；它对一步梯度延迟不敏感，又让异步流水线重新可行）。同时，数据管线——检查点加载、评估、模态数据变换——成了有名有姓的 GPU 小时损失来源。这一章的证据多是原型与单一测试床，结论比 A1/A5 弱，我会逐条标出。

> [!note] 为什么单独成章
> 第一轮把"训练并行"列为缺口。第二轮读到的材料不改变任何已有章节的结论，而是指向一个新判断：**"recipe 决定系统"**——这值得一个独立入口。数据管线并入本章，因为它和并行一样，都是"每一步之外"的 GPU 时间。

## 0. 旧基线

讲座把 DP/TP/PP/EP/CP 当作基础知识（本笔记不重复）。旧默认：同步训练、一次选定并行度数、AdamW、数据加载"喂得上就行"。

## 1. 规模扩展本身：公开可审计的数字

MLPerf Training v6.0（MLCommons，[2026-06-16](https://www.globenewswire.com/news-release/2026/06/16/3312914/0/en/correction-mlcommons-releases-mlperf-training-v6-0-results.html)）第一次加入 DeepSeek-V3（671B / 37B 激活 MoE）预训练基准。这是本笔记里少有的**经第三方审核规则的**训练数字（成绩由 MLCommons 审核，解读是提交者的）：

| GB300 GPU 数 | 达到目标质量时间 | 来源 |
|---|---|---|
| 2,048 | 5.54 min | CoreWeave 提交说明（[MLCommons 补充讨论](https://mlcommons.org/wp-content/uploads/2026/06/MLPerf-Training-v6.0-Supplemental-Discussion-UNDER-EMBARGO-UNTIL-6_16_26-8_00-AM-PT-1.pdf)，提交者自述） |
| 4,096 | 3.09 min | 同上 |
| 8,192 | 2.02 min | 同上；NVIDIA 博客表格一致 |

**我的推算**：强扩展效率 2,048 → 4,096 为 5.54 / (2 × 3.09) ≈ **90%**，2,048 → 8,192 为 5.54 / (4 × 2.02) ≈ **69%**。CoreWeave 称之为"接近线性"——这个说法与算术不符。MLPerf 是固定目标的"time-to-train"，越大规模每卡分到的工作越少，效率下降是预期的；它说明**在 8K 卡、固定问题规模下，通信与固定开销已占约三成**。

v6.1（2026-11-16）NVIDIA 称 Vera Rubin NVL72 上 DeepSeek-V3 从 256 卡到 1,024 卡"约 97% 效率"（16 → 约 4 分钟）（[NVIDIA 博客](https://blogs.nvidia.com/blog/mlperf-training-endpoints-vera-rubin/)）【厂商声明·成绩标为初步】——规模小一个量级，与上面不可直接比。v6.1 还新增了 RL 后训练基准，但 MLCommons 的说明页本轮无法打开，测什么未核实（见 [[A7 RL 后训练系统]]）。

NVIDIA 对 v6.0 的工程归因【厂商声明】：路由器从 FP64 改 FP32 使该 kernel 快 5×、端到端 +5%；流水线不平衡 <1%，端到端省 4%。**细节有用的地方在于**：在 MoE 预训练里，路由器、流水线平衡这类"小"环节已经是百分之几的量级。

## 2. 长度长尾：为什么静态 CP 度数浪费

### 2.1 一个可算的例子

**我的推算**：attention 的计算量与序列长度平方成正比。一条 128K 的序列 ≈ (128/4)² = **1,024 条 4K 序列**的 attention FLOPs。如果一个 global batch 里混着少数 128K 长样本和大量 4K 短样本：

- 按最长样本固定 CP=16，短样本也被切成 16 份，每份只有 256 token，通信与 kernel 启动占主导；
- 按短样本固定 CP=1，长样本放不下。

所以"按 micro-batch 重新配置 CP 组"是自然的方向。长尾不是假设：[[A2 Agent 负载]] 的 agent 轨迹（均值 68.7K–80.1K、最大 146K–166K token）正是后训练要喂的数据。

### 2.2 三个原型

| 工作 | 机制 | 条件与数字【均为作者测量，均为原型】 | 局限 |
|---|---|---|---|
| FCP（HKUST-GZ + 华为，[arXiv:2602.21788](https://arxiv.org/abs/2602.21788) v2，2026-06-08） | 每个 micro-batch 重新分 CP 组，允许任意整数度数；先装箱再二维 DP 求解 | 4 节点 × 16 张昇腾 910C，128K 最大长度；文本 LLM 对 Megatron/DeepSpeed 最优者 1.05–1.37×，多模态 1.14–1.38×；求解 ≤86 ms | 作者明说"数据均衡时收益递减" |
| Concertina（清华等，[arXiv:2509.21275](https://arxiv.org/abs/2509.21275)） | 动态流水线：按负载平衡切块，结合块级自适应重计算，ILP 联合优化 | 32×A800，48K–192K；对 FlexSP 最高 1.69×、对 MEPipe 1.40× | MoE 只在均衡路由下检查；基线由作者增强 |
| AutoSP（UIUC 等，[arXiv:2604.27089](https://arxiv.org/abs/2604.27089)） | 编译器 pass 自动插入 Ulysses 式 all-to-all + 按序列长度的重计算 | 8×A100，最大可训练上下文对编译后 ZeRO-3 最高 5.6×，对 DS-Ulysses/Ring 约 2–3×；运行时约 0.97× | 只到 13B、8 卡 |

**读法**：三者从不同层（调度、流水线、编译器）解决同一个问题——长度长尾——说明它已是共识瓶颈；但都没有千卡以上的公开结果。

## 3. 优化器改变并行方式

### 3.1 Muon 需要完整矩阵

Muon 用 Newton–Schulz 迭代对每个权重矩阵做正交化，需要**完整矩阵**；而 FSDP/ZeRO 把矩阵切碎了。朴素做法是每个 rank 都 gather 再算，重复计算。DeepSeek-V4（§2.4）与 Engram 论文都用 Muon 训练，所以这不是边缘问题。

DMuon（X Square Robot，[arXiv:2606.27153](https://arxiv.org/abs/2606.27153) v1，2026-06-26）【作者测量】：每个矩阵指定一个"所有者" rank 计算、两级（节点内/节点间）通信、Gram 空间 NS + 对称 kernel，所有者分配用实测代价的 MILP。A800、8–256 卡：端到端步长比朴素 Muon 快 1.48–3.01×；平均比 AdamW 多约 2%（逐行范围 0.2%–17.6%，【摘要级】）。作者明说只去掉系统开销、不去掉算法本身的代价；称已用于自家模型的生产训练（自述）。

### 3.2 Muon 让异步流水线重新可行

异步流水线（PipeDream-2BW 式，恒定一步梯度延迟）能消除气泡，但 AdamW 在延迟梯度下明显退化。ICML 2026 论文（Yandex / ISTA / MBZUAI，[arXiv:2606.30634](https://arxiv.org/abs/2606.30634)）【作者测量】：

| 设置 | 同步 | 异步 | 差距 |
|---|---|---|---|
| 360M，AdamW | 2.612 | 2.890 | +0.278 |
| 360M，Muon | 2.578 | 2.590 | +0.012 |
| 10B MoE、200B token，Muon | 1.906 | 1.911（加误差反馈 1.906） | 约 0 |

这就是"recipe 决定系统"最直接的例子：**换了优化器，一个被放弃多年的并行方式（异步 PP）重新进入候选**。局限：只有一个 10B 对比、超参只在 135M 上扫、作者承认缺少机制解释、不外推到万亿 token。

## 4. 数据管线：每一步之外的 GPU 小时

- **OSDI 2026 最佳论文**（ByteDance Seed + USTC，[OSDI '26](https://www.usenix.org/conference/osdi26/presentation/chen-luofan)，本轮只读到摘要）：三个"少被报告"的瓶颈——从远端检查点评估训练中模型带来的跨数据中心流量；启动时的检查点加载 I/O 争用；多模态数据加载时的 CPU 重变换。做法：全局命名空间的预测式检查点复制、热文件主动复制、把数据变换卸载到存储层的 CPU。摘要称：每次评估浪费的 GPU 小时 16,800 → 4,000；启动检查点加载时间 −40.8%；数据加载导致的停顿 −63.2%【作者自述；基线与规模未读到】。
- 与 [[A8 万卡故障与 goodput]] 的连接：Lablup 504 卡集群的重启加载平均 33 分钟，TrainMover 测得 8,192 卡常规重启 69% 花在初始化。**检查点加载既是数据管线问题，也是容错问题**。
- 后训练的数据管线：DeepSeek-V4.1 报告说其 SFT → RL → 在线蒸馏"没有算法创新"，变化在数据管线——以（问题，环境，验证器）三元组组织任务（V4.1 §5.1）。这意味着后训练的"数据"本身包括可执行环境，见 [[A7 RL 后训练系统]]。

## 5. 代价搬到哪里

| 设计 | 省下 | 代价搬到 |
|---|---|---|
| 按 micro-batch 动态 CP/PP | 长尾样本的浪费 | 每步求解与重配通信组、代价模型误差（FCP <8%、Concertina <5%） |
| 编译器自动 SP | 侵入式改模型代码 | 依赖手工维护的算子集合 |
| 所有者式分布式 Muon | 重复 NS 计算 | 所有者负载不均、MILP 分配 |
| 异步 PP + Muon | 流水线气泡 | 一步延迟的收敛风险、需要误差反馈；绑定优化器选择 |
| 检查点预测复制、存储侧变换 | 评估与启动的 GPU 空转 | 存储层 CPU 与跨机房复制带宽 |

## 6. 何时反转

| 条件 | 结论 |
|---|---|
| 数据长度均衡（预训练打包到固定长度） | 动态 CP 的收益递减（FCP 作者原话），静态配置足够 |
| 用 AdamW | 异步 PP 的退化重新显著（360M 差距 +0.278） |
| 小规模（≤256 卡） | 分布式 Muon 的开销本身不大；DMuon 在大卡数下也逐渐收敛到 AdamW 水平 |
| 固定问题规模扩到万卡 | 强扩展效率下降（MLPerf DeepSeek-V3：2K→8K 约 69%），更多卡主要换来时间而非效率 |
