# A13 多模态与端侧推理：服务单位从"token 循环"变成"阶段图"，端侧加速器只改变 prefill

> [!abstract] 一句话
> 两个方向第一轮都没有采样，第二轮读完后发现它们共享同一个底层事实——**prefill 受算力限制、decode 受带宽限制，而一次请求越来越由多个异构阶段组成**。多模态服务（文本 LLM + 语音 talker + 扩散生成）因此从"一个引擎跑一个自回归循环"变成"一张阶段图、每个阶段一个引擎、阶段之间是连接器"；端侧推理则用实测反复证明：新的 NPU / 矩阵单元大幅加速 prefill，但几乎不改变 decode。

## 0. 旧基线

讲座按场景分层介绍推理（[视频 55:08](https://www.bilibili.com/video/BV1vmzXBBESY/?t=3308)），重点是数据中心 LLM。多模态和端侧在第一轮被列为缺口。

## 1. 多模态服务：阶段图

### 1.1 Workload 要什么

"任意到任意"模型（如 Qwen3-Omni：Thinker LLM → Talker → 声码器；BAGEL：理解 + 生成；Wan2.2：视频扩散）把一次请求拆成多个阶段，每个阶段的计算形态不同：自回归 decode 受带宽限制，扩散步受算力限制，编码器一次性大 batch。用一个面向"逐 token 步"设计的引擎跑整条链，要么让快阶段等慢阶段，要么开发者手写编排。

基准开始跟上：MLPerf Inference v6.0（约 2026-04-01，[MLCommons 公告](https://groups.google.com/a/mlcommons.org/g/public/c/TFU4lsU-e0A)）加入视觉-语言模型和文生视频基准；DeepSeek-R1 新增更严格延迟的交互场景。

### 1.2 两个系统，两种图

| | vLLM-Omni | M* |
|---|---|---|
| 来源 | 华为等，[arXiv:2602.02204](https://arxiv.org/abs/2602.02204) v1，2026-02-02；代码 [vllm-project/vllm-omni](https://github.com/vllm-project/vllm-omni) | Stanford / UW / CMU，[arXiv:2606.12688](https://arxiv.org/abs/2606.12688) v2，2026-06-13 |
| 抽象 | **阶段 DAG**：节点是阶段，边是用户定义的传输函数；每阶段独立引擎（AR 用 vLLM，DiT 用新扩散引擎）、独立 batching 与 GPU 分配 | **Walk Graph**：计算图 + 命名的"走法"，原语包括顺序、并行、循环、动态循环（每请求提前退出）、流式边 |
| 数据面 | 单节点共享内存；跨节点 Ray + Mooncake 连接器（TCP/RDMA） | ZeroMQ + Mooncake |
| 数字【作者测量】 | Qwen3-Omni 作业完成时间对基线最多 −91.4%；Qwen2.5-Omni 对 HF Transformers RTF −61.4%；连接器开销约 0.5–8.3 ms | BAGEL 文生图 p50 延迟比 vLLM-Omni 低约 20%；Qwen3-Omni TTS（batch 16）RTF 最多低 2.9×、吞吐高 2.7× |
| 局限 | 部分收益来自基线缺少的图编译，架构与实现效应混在一起 | 原型，代码承诺在定稿时开源；只实现了 TP |

**读法**：M* 批评阶段 DAG 表达不了阶段内的循环与并行（例如 CFG 的三路并行、世界模型的 rollout 循环）——这和 [[A3 分离的下一层]] 的逻辑相同：**每拆一次就新增一个连接、一个比例**，而图越复杂，调度器越需要知道"下一步走哪条边"。

> [!warning] 名称冲突
> DeepSeek-V4.1 报告里的 "EPD 分离"（Encoder–Prefill–Decode）指的是它自己的**编码器–解码器语言模型**结构（CED）中编码器阶段单独部署（V4.1 §3.2），不是多模态编码器分离。vLLM v0.34.0 中的 `--mm-encoder-tp-mode data`、Pixtral/Mistral3 编码器 CUDA graph 才是多模态编码器侧的工程项。

### 1.3 训练侧的对应

多模态把代价也搬到了数据管线：OSDI 2026 最佳论文把"多模态数据加载时的 CPU 重变换"列为三大瓶颈之一，做法是卸载到存储层 CPU（见 [[A12 训练并行与数据管线]]）；FCP 在 InternVL3 / Qwen3-VL 上的动态 CP 收益（1.14–1.38×）高于纯文本（1.05–1.37×），因为视频样本长度更不均衡。

## 2. 端侧：同一个 prefill / decode 二分法

### 2.1 三组实测

| 研究 | 硬件 | 发现【均为作者测量】 |
|---|---|---|
| Leiden 大学（[arXiv:2605.27435](https://arxiv.org/abs/2605.27435)，2026-05-22），llama.cpp b7588 | 骁龙 8 Gen 3，Hexagon v75 NPU | prefill 的矩阵乘 **CPU 比 NPU 快 1.27–1.62×**；decode 的矩阵乘 NPU 快 1.55–1.67×，但端到端 decode 只快 **1.05–1.20×**；decode 中通信开销占 9.9–13.0%；全量 NPU 卸载使耗电增加 22–51%（随提示长度） |
| BaseRT（Base Compute，[arXiv:2607.19438](https://arxiv.org/abs/2607.19438)，公司自测） | Apple M5 Pro，Metal 4 张量 API | prefill 对 llama.cpp 最高 6.4×、对 MLX 3.9×（用 M5 的矩阵单元）；decode 对 llama.cpp 最高 1.75×、对 MLX 1.33×，**来自调度与融合，不是矩阵单元**——作者明说 decode 是 M=1 的 GEMV，张量单元帮不上 |
| ExecuTorch（Meta，[arXiv:2605.08195](https://arxiv.org/abs/2605.08195)，MLSys 2026） | Galaxy S25 Ultra CPU | Qwen3 0.6B decode ExecuTorch 72 tok/s vs llama.cpp 98；Llama 3.2 1B 持平；prefill 接近。作者称"每天数十亿次推理"（自述，无数字） |

### 2.2 一个可算的例子

**我的推算**：Phi-4 Mini 约 3.8B 参数，4-bit 量化约 2 GB；decode 每 token 至少读一遍权重。llama.cpp 在 S25 Ultra 上 22.1–22.9 tok/s ⇒ 有效读带宽约 2 GB × 22 ≈ **44 GB/s**——已是手机 LPDDR 的量级。换句话说，**端侧 decode 的上限由"每 token 要读多少字节"决定**，加多少矩阵单元都不改变它。能改变它的是：更少激活参数（BaseRT 在 Qwen3.6-35B-A3B 这类 MoE 上 decode 达到 110.7 tok/s，因为每 token 只激活约 3B）、更低比特、或投机解码。

这与数据中心是同一张图：[[A3 分离的下一层]] 的 LPX 用 SRAM 加速 decode、[[A9 硬件分工化]] 的 TPU 8i 加大片上 SRAM——都是在攻"每 token 读字节"。

### 2.3 桌面级"边缘"：大表落盘

DGX Spark / Mac 这类大内存终端上，DeepSeek-V4.1 的 Engram 表成为可选卸载对象：社区引擎 ds4 把约 189 GiB 的表留在本地 SSD（[dwarfstar 博客](https://dwarfstar.sh/blog/deepseek-v41-engram-ssd/)，2026-09-13，【社区自述·无测量】）；vLLM v0.34.0 为 Qwen3.8 的 PLE 表加入磁盘卸载，DGX Spark 上少用 27 GiB。是否可行取决于表在第几层被读，见 [[A11 条件记忆 Engram#3. 一个可算的例子：带宽不是瓶颈，截止时间才是]]。

## 3. 代价搬到哪里

| 设计 | 省下 | 代价搬到 |
|---|---|---|
| 阶段图 + 每阶段独立引擎 | 阶段间等待、手写编排 | 连接器延迟、阶段间资源比例、调度复杂度 |
| 循环/并行原语（M*） | 每模型胶水代码 | 运行时状态机、调试难度 |
| NPU 卸载 | CPU 占用、部分 decode 时间 | 通信开销、耗电、prefill 反而更慢 |
| 统一导出栈（ExecuTorch） | 多套转换与重写 | 动态形状与数据相关控制流的导出困难；某些 decode 比专用运行时慢 |

## 4. 何时反转

| 条件 | 结论 |
|---|---|
| 单一模态、单一阶段（纯文本 LLM） | 阶段图没有必要，常规引擎即可 |
| 多模态但阶段间负载均衡且同置 | 分离带来的连接开销可能超过收益（vLLM-Omni 在 Qwen2.5-Omni 上的收益远小于 Qwen3-Omni） |
| 端侧长提示 + 短输出 | prefill 占主导，矩阵单元（M5）收益大 |
| 端侧短提示 + 长输出 | decode 占主导，NPU / 矩阵单元收益小（1.05–1.20×），优先压缩每 token 读字节 |
| 电池受限 | 全量 NPU 卸载可能更耗电（+22–51%） |
