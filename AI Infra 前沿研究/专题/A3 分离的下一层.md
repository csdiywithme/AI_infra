# A3 分离的下一层：P/D 角色可切换、Attention/FFN 可拆、芯片按阶段分工

> [!abstract] 一句话
> P/D 分离从"拓扑选择"变成"可在线调整的角色"；在 NVL72 这样的大 scale-up 域里，attention 与 FFN 也开始被拆到不同 GPU；硬件层面，NVIDIA 把 decode 交给 SRAM 型的 LPX，同时**撤下了**专做 prefill 的 CPX。共同逻辑：按瓶颈把阶段放到不同资源，但每拆一次就新增一个比例要调、一条链路要藏。

## 0. 旧基线与一条仍然有效的边界

讲座以 DistServe 为源头介绍 PD 分离（[视频 1:10:35](https://www.bilibili.com/video/BV1vmzXBBESY/?t=4235)）。旧笔记补充的边界本轮再次核对仍成立：vLLM 文档原文 "Disaggregated prefill DOES NOT improve throughput"，其价值在于独立调节 TTFT / ITL（[vLLM docs](https://docs.vllm.ai/en/latest/features/disagg_prefill/)，2026-11-23 核对，latest 文档）。

## 1. 角色变成可调的

- SGLang v0.5.21（2026-10-02）：**PD 实例可在线在 prefill 与 decode 之间切换**【已发布】（[SGLang releases](https://github.com/sgl-project/sglang/releases)）。
- PrfaaS 的长时间尺度调度也重平衡 P/D 节点角色（[arXiv:2604.15039 §3.4.3](https://arxiv.org/abs/2604.15039)）。
- llm-d v0.9.0（2026-08-17）：P/D 的预测延迟路由、KEDA 自动扩缩【已发布】（[llm-d releases](https://github.com/llm-d/llm-d/releases)）。

**为什么需要**：P:D 最佳比例取决于输入/输出长度分布与命中率，而 [[A2 Agent 负载]] 显示 agent 负载 decode 占比极高、且会随任务阶段变化；静态比例会长期失配。

## 2. Attention / FFN 分离（AFD）

**机制**：attention worker 持有 KV、做 attention、路由和采样；FFN/MoE worker 持有专家，把来自多个 attention worker 的 token 聚成更大的专家 batch。decode 时 attention 受 KV 读带宽限制、专家 GEMM 受 batch 太小限制——拆开后两边各自达到更好的利用率。2025 年 MegaScale-Infer 已提出（[arXiv:2504.02263](https://arxiv.org/abs/2504.02263)，本轮未精读，作基线）。

**新进展：FastAFD**（UCSD Hao AI Lab，[博客](https://haoailab.com/blogs/fastafd/)，2026-07-06）【原型】：
- 在一个 NVL72 NVLink 域内做 M2N/N2M dispatch/combine（改自 DeepEP），FFN 侧用 MegaMoE 风格的持久化融合 kernel，2 micro-batch 流水。
- 作者论点："在一个 NVLink 域里，通信应该在 GPU 上。"——AFD 的可行性来自 **scale-up 域足够大**，attention↔FFN 的边界不出机架。
- 【作者测量】Qwen3-235B-A22B-FP8 与 MiniMax-M2.5 FP8、8K/16K 上下文，**纯 decode**：每 GPU（含 FFN GPU）稳态吞吐比调优后的同置 vLLM（DP=4, EP=4, DeepEP+DeepGEMM）高 1.35–1.45×；最佳 M:N 为 17:1（MiniMax）、7:1（Qwen 8K）、11:1（Qwen 16K）。
- 不含 prefill、在线到达、投机解码、故障恢复；代码发布状态博客前后表述不一致（TL;DR 说已开源，正文说计划发布）。

| 2026-08-31 | 分析师称 CPX 改为 HBM4 重新设计、1Q27 量产 | 未证实（二手转述分析师帖子） |

**解读**：CPX 的前提是"prefill 算力密集、不需要 HBM 带宽，可以用便宜显存"。但 [[A1 KV 状态变小之后]] 和 [[A2 Agent 负载]] 指向另一面：高命中的 agent 负载 prefill 占比小、decode 占大头。LPX 押注的是 decode 的**单用户速度**。NVIDIA 宣称 Gemma 4 31B、100K 上下文下 3,400 输出 token/s（引 Artificial Analysis），但未说明是单用户还是聚合、batch 多大【厂商声明】；Futurum 依据 Hot Chips 描述其为"LPX 起草、GPU 校验"的外部 drafter 投机解码（[Futurum](https://futurumgroup.com/insights/nvidia-groq-3-lpxs-promise-of-worlds-fastest-inference-enters-full-production/)，2026-09-14，分析师二手），NVIDIA 博客本身未提此机制。

**第二轮补到的一手规格**（[LPX 产品页](https://www.nvidia.com/en-us/data-center/lpx/)，2026-09-21 更新）【厂商声明】：每颗 LPU 500 MB SRAM、150 TB/s SRAM 带宽、2.5 TB/s scale-up 带宽；每机架 256 颗，合计 128 GB SRAM、12 TB DDR5、40 PB/s。产品页对分工只有一句："Rubin GPU 与 LPU 为每个输出 token **共同计算模型的每一层**"。

**唯一的第三方数字**（[Tom's Hardware，2026-08-26，Hot Chips 报道](https://tomshardware.com/tech-industry/semiconductors/nvidia-presents-groq-3-lpx-architecture-and-unveils-its-first-third-party-inference-benchmark)）：Artificial Analysis 在一个**私有、预发布**的 Gemma 4 31B 端点上测得 3,431 输出 tok/s（100K 上下文、**并发 1**、50 次顺序请求的中位数），约为次快公开端点（870 tok/s）的 4×；文章自己指出对照组是共享的生产 serverless 端点，不可直接比较。NVIDIA 台上演示的 10,996 tok/s 是自测。【摘要级】报道称 NVIDIA 介绍了三种组合方式：P/D 分离、attention/FFN 分离、外部 drafter 投机解码。

**我的推算**：128 GB SRAM / 机架。一个 1T 参数模型即使 FP4 也要约 500 GB，**单机架 SRAM 装不下整套权重**，所以"共同计算每一层"大概率意味着权重或部分层仍在 GPU HBM 上——这与"LPX 接管 decode"的直觉不同。这是推断，等待一手分工说明。

> [!warning] 证据边界
> 现有数字只证明**单用户速度**（并发 1）；每兆瓦吞吐（"最高 35×"）在产品页上标为预测（见 [[A14 电力与成本#2.3 decode 专用芯片的每兆瓦声明]]）。不要把它当作"decode 已被 SRAM 芯片接管"的证据。

## 4. 代价搬家

| 拆分 | 省下 | 新增 |
|---|---|---|
| P/D | 阶段干扰、独立 SLO | KV 传输、P:D 比例、跨池背压 |
| P/D 角色在线切换 | 比例失配 | 切换时的权重/缓存预热、CUDA graph 重捕获（SGLang v0.5.21 为 elastic EP 加了重捕获） |
| AFD | decode 时专家 batch 太小 | M:N 比例、每层两次跨 GPU 往返、对 scale-up 域大小的依赖 |
| 异构芯片（GPU + LPX） | decode 延迟 | 两套编译/运行时、数值一致性（见 [[A6 数值一致性]]）、采购与容量规划 |
| 编码器阶段单独部署（DeepSeek-V4.1 的 EPD：Encoder–Prefill–Decode） | 编码器–解码器模型里编码器与解码器的计算形态不同 | 第三个比例要调、编码器输出的传输（V4.1 §3.2，未给数字） |
| 多模态阶段图（vLLM-Omni、M*） | 阶段间互相等待 | 连接器与阶段资源比例，见 [[A13 多模态与端侧推理]] |

## 5. 何时反转

- **scale-up 域小**（8 卡 HGX、PCIe）：AFD 每层往返出机箱，FastAFD 的论据不成立。
- **prefill 主导**（长文档、低命中）：decode 专用芯片的价值下降，CPX 类思路回归——这正是 NVIDIA 说 CPX "仍是好主意、下一代再考虑"的语境。
- **吞吐而非延迟**是目标：vLLM 文档的边界依然成立，分离本身不提高吞吐。
