# 我们究竟在优化什么

[[00 AI Infra 整体主线|整体主线]] → 本章 → [[02 一张 GPU 上时间和显存花在哪里|下一章：一张 GPU 上时间和显存花在哪里]]

我们要做一个代码助手：读入一段代码与问题，生成修改建议，之后还会运行测试并利用反馈改进模型。先把范围收窄到第一件事——训练或微调一个文本模型，再让它生成回答。这样，每引入一种系统设计，都有同一个问题可问：它怎样帮助这个助手完成工作？

全文使用同一组[[算例与符号约定|教学设定]]：约 8B 参数、32 层、隐藏维度 4096，权重用 BF16；输入 4096 token，最多生成 256 token。每张卡有 48 GB 显存，矩阵计算预算 200 TFLOP/s，显存带宽预算 1 TB/s。这些数字用于手算，不对应某个模型或设备的实测成绩。我们会逐步发现，这张卡装得下权重，却装不下这里选定的完整训练状态。

## 先说明怎样才算完成工作

代码助手回答得流畅，不一定能给出正确修改。应先选择代表性任务，用独立的检查或测试判断结果，再约定允许的时间与资源。否则，把提示缩短、降低精度、减少训练数据带来的速度变化，都可能混入任务变容易或质量下降的影响。

训练中能直接得到一个损失值：模型对给定目标预测得有多差。它为更新参数提供方向，却不等于代码能通过测试。InstructGPT 同时检查行为偏好和已有任务表现，说明训练目标与最终用途之间仍须验证。[InstructGPT，v1，方法与评估](https://arxiv.org/html/2203.02155v1)

因此，先固定一个比较条件：相同模型、数据、输入长度、数值要求和任务质量下，完成工作要多久、占多少资源。以后若主动改变数据或模型，就重新验证它是否达到同一目标。前者主要改执行效率，后者还改变了需要执行的工作。

## 一串 token，怎样变成可以计算的东西

文本先被编码成 token 编号。一个 token 不等于一个汉字或一个代码字符；这里的 4096 指编号的个数。模型通过查表把每个编号变成一个长度为 4096 的向量。把各位置排起来，就得到形状为 $[4096,4096]$ 的张量 $X$：第一维是位置数，第二维是每个位置的表示宽度。

这一点值得先记住：输入长度决定有多少行，隐藏维度决定每行有多少元素。BF16 每元素 2 bytes，所以这一个张量有 $4096\times4096\times2=33554432$ bytes，即 32 MiB。它是一次计算产生的表示，通常称为激活；它与模型参数不是同一个对象。

为了看清一层内部的工作，先只展开其中一个前馈子层，即 MLP。取中间宽度 $h=16384$，用下面的简化计算：

$$
R=XW_1,\qquad H=\phi(R),\qquad Y=HW_2.
$$

$W_1$ 的形状是 $[4096,16384]$，把每行扩宽；$\phi$ 是逐元素非线性；$W_2$ 的形状是 $[16384,4096]$，把宽度变回去。于是 $R,H$ 有 4096 行、16384 列，$Y$ 又回到 $[4096,4096]$。前一层的输出成为后一层的输入，32 层要沿这个方向接着算。

这里的两块权重只是用来理解局部矩阵计算。实际模型还包括 Attention、门控、词表等部分，不能把这个简化 MLP 乘以层数，反推全文的 8B 参数。跨位置的信息怎样组合，会在第 04 章展开；本章先把“输入、权重和中间结果”分清。

## 训练与生成，沿着同一条计算线做什么

训练数据提供已知文本及相应目标。例如，在某个位置看见代码前缀后，希望模型提高真实后续 token 的概率。模型先前向计算，得到预测分布与损失，再反向计算：每个参数改变一点，损失会怎样变化？这个变化率就是梯度。优化器根据梯度和需要保留的历史状态更新参数，一次更新由此完成。

训练时，供本次计算使用的 token 已经给定；因果遮罩限制各位置读取哪些历史信息，并不要求像线上回答一样，先生成第一个位置再生成第二个位置。所以同一层可以同时处理许多已知位置。它们仍然要先经过这一层，才能进入下一层；不同位置并行与不同层有依赖，是两件事。

生成则多了一条依赖：读完 4096 个输入 token 后，模型先给出第一个输出的分布；选出的 token 成为下一轮输入，才能继续选择后面的输出。最多 256 个输出因此不能简单当作 256 个早已知道的输入位置。第 05 章会沿这条依赖解释两个推理阶段及历史状态。

全文用 $B$ 表示序列数，用 $M$ 表示一次矩阵调用的 token 行数。训练时若一起处理 $B$ 条等长的 4096-token 序列，本例的 MLP 有 $M=4096B$ 行；普通逐步生成时，每条序列新增一个位置，便有 $M=B$。写清行数，才能比较实际做了多少计算。

## 数据与配方为什么也属于资源问题

同样的训练 token 数，可以来自不同内容、混合比例与长度分布。内容决定学习什么，长度与打包方式决定矩阵形状，监督掩码决定哪些位置贡献损失。填充多的运行即使报告很高的吞吐，也未必完成了同样多的有效训练。因此要一起记录数据、结构、目标函数、优化器、批量和训练日程。

参数更多意味着有更多状态，也有更多矩阵计算；看过更多数据意味着重复执行更多次更新。固定预算时，两者怎样分配也是优化问题。Chinchilla 研究的是这种预算分配；它在特定模型、数据和实验下建立的经验关系，不能直接变成所有任务的最佳配方。[Chinchilla，v1，第 3 节](https://arxiv.org/html/2203.15556v1)

至此，问题已经能落到具体对象：一次调用有多少行、权重有多大、哪些结果需要留到反向、总共要处理多少训练 token。[[02 一张 GPU 上时间和显存花在哪里|下一章]]就用这个 MLP 逐项数运算和字节，算清为什么同一张卡有时忙于计算，有时忙于搬数据。

> 预训练用大量上下文预测后续 token；SFT 用希望模型模仿的行为示范。二者都可在已知序列上做前向、损失与反向，但数据、监督位置和行为目标不同。偏好学习使用“哪个回答更好”的信号，是一类目标，不等于某一种 RL 流程。DPO 直接利用偏好对更新策略，其微调循环不必采样回答，也不必先训练显式奖励模型。[DPO，v2，第 4 节](https://arxiv.org/html/2305.18290v2)
>
> InstructGPT 的 RLHF 还包括奖励模型训练，以及策略生成、评分与更新；不同 RL 方法的奖励、采样和更新方式并不相同。先理解训练和生成各自怎样运行，再进入[[07 当生成结果又参与模型更新|第 07 章]]，就能看清这些新增环节为何带来系统协调问题。[InstructGPT，v1，第 3 节](https://arxiv.org/html/2203.02155v1)
>
> 一次运行变快也不等于更早得到可用模型：数据错误、数值不稳定或不合适的评估，会让实验重做。贯穿后文的目标仍是达到约定质量所需的有效计算、实际时间与资源，以及结果能否复现和继续使用。
