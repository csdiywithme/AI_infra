# 06 当许多请求同时到来

[[00 AI Infra 整体主线|整体主线]] · 上一篇：[[05 从模型权重到一次生成]] · 下一篇：[[07 当生成结果又参与模型更新]]

上一章让多条序列一起 decode：约 16 GB 的权重读取可以被更多 token 摊薄，但 KV 与每轮时间也在增加。现在还是同一台设备、同一个 8B 代码助手，以及 4096-token 输入、最多 256-token 输出。只增加一个条件：请求不再一起准备好，而是在不同时间到达。

## 一条新请求到达，谁会为它等待

先使用最简单的静态组批：收齐一批输入，完成 prefill，再不断 decode，直到整批结束。它有两个问题。等待凑批会延后首 token；开始生成后，短请求退出留下的空位又难以及时接纳新请求。即便所有请求长度暂时相同，只要到达时间不同，也会有人等待下一批。[Transformer Inference：引擎组织](https://jax-ml.github.io/scaling-book/inference/)

于是把调度单位缩小到一轮：本轮完成者退出，空位在后续轮次接纳新请求，这就是连续批处理的基本思路。可是新请求还没建立 KV，不能直接塞进 decode。它先要 prefill，而这段工作也使用同一台设备。[Orca，OSDI 2022](https://www.usenix.org/conference/osdi22/presentation/yu)

用一条时间线观察冲突。假设一次含 32 条序列的 decode 用 40 ms，一条完整输入的 prefill 用 400 ms。这两个时长是教学示意，不是实测；分别高于本例约 33.18 ms 的数据读取账和约 328 ms 的主要矩阵计算预算。暂忽略额外重排、调度与通信，历史长度也保持在本例容量范围内。

在某轮 decode 刚输出后，新请求 R 到达。如果马上为 R 做完整 prefill，再继续原来的 32 条 decode，那么老请求距离下一次输出，要等约 $400+40=440$ ms。R 可能较早获得首 token，其他用户却看见长停顿。这里先只分析老请求的间隔；R 后续何时加入 decode，还要由空位与接纳策略决定，不能假定凭空多出一个槽位。

如果一直优先老请求，新请求的队列又会增长。到达的不只是一批输出 token：每条请求还带来一次输入处理和一段持续占用的 KV。因此不能把上一章某个 decode tokens/s 直接除以 256，就当作线上每秒请求容量。

## 把长输入切开，究竟改善了谁的时间

现在只改变 prefill 的安排：把这条输入分成 8 块，每块假设用 50 ms，每块之间插入一次 40 ms 的 decode。这个例子仍按总计 400 ms 的 prefill 工作估算，实际分块可能增加读写、调度或重排开销。

老请求便可以每约 $50+40=90$ ms 输出一轮，而不必经历一次 440 ms 的长间隔。但新请求要等 8 块全部完成，首 token 才能产生；中间插入 7 轮 decode，R 的这段时间就成为 $8\times50+7\times40=680$ ms。我们把长时间独占改成较频繁的交替，改善了老请求的节奏，同时延后新请求完成输入处理。

块更小可能提供更多调度机会，也可能降低矩阵效率；给 decode 更多优先权，也会增加输入排队。这就是 chunked prefill 要调节的取舍，不是把一项计算拆开便消除了它的成本。Sarathi-Serve 用分块与组批安排研究这类问题。[Sarathi-Serve，OSDI 2024](https://www.usenix.org/conference/osdi24/presentation/agrawal)

到这里再定义指标就有了对象。TTFT 是请求从提交到首 token 的时间，包含排队及执行链上的等待；ITL 观察相邻输出间隔。TPOT 是请求生成阶段的平均每 token 时间，可能掩盖上例的一次长停顿。必须说明统计口径与分位数，不能用一个平均数代替全部体验。

应用可以分别约定首 token 和生成节奏的服务目标。在固定硬件、质量和流量下，每秒有多少请求满足这些目标，才是这里关心的有效吞吐。继续增加到达压力，可能只增加超时和队列；只汇总 tokens/s 会漏掉这种失败。DistServe 用首 token、生成延迟约束下的 goodput 表达这类目标。[DistServe v3，§1–2](https://arxiv.org/html/2401.09670v3#S1)

## 多一个副本以后，为什么还不能只选最空的

单台设备的时限与容量明确后，再增加副本。请求可以去别处排队，局部拥塞因此有机会缓解；但每个副本的队列与缓存位置也开始不同。

现在启用上一章的前缀复用。例如 R 的系统提示和部分代码已经在副本 A 计算过，A 却正忙；副本 B 很空，但没有这些状态。路由要比较等 A、取回状态与在 B 重算的完成时间，不能只按命中率或请求数选择。输入输出长度也会改变预计工作量：相同请求数不一定代表相同负载。

缓存还要占空间。前章 512 MiB 的前缀若长期留在 HBM，会挤占活跃序列的增长余量；放到主机内存或更低层存储能扩大保留范围，却要付出读取和管理成本。取回是否比重算值得，需要沿同一条请求的时限比较，而不是只比存储容量。Mooncake 围绕 KV 的放置、复用和转移组织调度，同时处理远端读取与拥塞。[Mooncake v1，§1、5](https://arxiv.org/html/2407.00079v1#S5)

> [!example]- KVStream：增加存储副本，也可能增加无效写入
> KVStream 的论文原型在 NVMe 与并行文件系统保存副本，同时读取，并让较快路径接手尚未完成的块，以组合带宽；代价转移到副本写入和后台 IO。作者的某条 Chutes trace 随 DRAM 增大，TTFT 加速比从 1.71 降到 0.98：读取需求下降后，额外写入仍在发生。因此要同时核算复用距离、DRAM 容量、读写比例与请求顺序，不能推成“缓存或层数越多越快”。这是作者原型的负载敏感性实验，不代表稳定服务能力或跨 backend 通用结果。[KVStream v1，设计与敏感性实验](https://arxiv.org/html/2610.31827v1) · [[来源与证据#AIINFRA-E-20261026-05|负载、硬件与实现边界]]

## 单独准备 prefill 资源，新增了哪条路径

回到老请求被新输入打断的问题。除了在单池内切块调度，还可以把 prefill 与 decode 放到不同资源池。这样可分别安排并行方式和资源比例，减少两个阶段的直接干扰；代价是阶段之间必须交接状态，而且两个池会各自排队、分别占用权重等资源。

本例完成 4096-token 输入后，有 512 MiB 的 KV。若经单向有效载荷 50 GB/s 的链路交接，仅搬这些字节就约需：

$$
536870912/(50\times10^9)\approx10.7\ \text{ms}.
$$

这个数未计排队、启动、网络竞争、布局转换和同步；真正的交接还要说明状态何时完整可用、目标引擎何时接纳。首 token 何时返回，也取决于具体流水线。第 05 章的混合模型案例提醒我们，某些结构还需交接 KV 之外的状态。

于是问题变成：减少的阶段干扰是否超过新增的搬运与等待？输入输出比例、SLO、互连和资源比例共同影响答案。一个池空闲、另一个拥塞时，GPU 总数充足也不能自动兑现低延迟。DistServe 将阶段放置与带宽条件纳入优化，其特定结果不能推出 PD 在所有负载上都优于共置。[DistServe v3，§3–4](https://arxiv.org/html/2401.09670v3#S3)

> DeepInfer 公开离线推理和核心引擎，但 README 明确不包含完整 KV 系统、VE/Prefill/Decode 拆分服务和跨 DP 副本负载均衡。部署 Q&A 对 3FS、长时缓存与路由的描述可帮助理解内部设计，不能证明整套服务已随源码交付。第 05 章的局部算法证据也不能自动升级为这里的线上容量与可靠性结论。[公开范围](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/README.md) · [作者部署 Q&A](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/doc/inference_deployment_qa.md)

比较一次服务改动，要保持硬件、质量、请求长度分布与到达压力一致，同时看等待、延迟尾部、有效吞吐、KV 占用和抢占重算；发生过载时还要报告拒绝与超时。批量、分块、路由和拆分，都是在安排这条执行路径中的工作与等待。
