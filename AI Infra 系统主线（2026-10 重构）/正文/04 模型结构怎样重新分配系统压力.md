# 04 模型结构怎样重新分配系统压力

[[00 AI Infra 整体主线|整体主线]] · 上一篇：[[03 一张卡放不下跑不完以后]] · 下一篇：[[05 从模型权重到一次生成]]

前面已经把代码助手的训练工作放到设备上。现在要拆开这个模型，确定究竟在计算什么。沿用 [[算例与符号约定]]：约 8B 参数、32 层、隐藏维度 4096，32 个 query heads、8 个 KV heads，每头 128 维。我们先观察一层；算例中的简化图用于理解依赖，不用于反推完整 8B 参数。

## 同一个位置经过什么，不同位置又在哪里相遇

先取一条序列的 $M$ 个已知位置，当前层输入为 $X[M,4096]$。沿用第 02 章的简化前馈层，它先投影到 16384 维，经过非线性，再投影回 4096 维。各位置使用同一组权重；在这个前馈块内部，一行输出不需要读取另一行的输入。实际模型还可能有门控等分支，这里暂不展开。

Attention 不同。它先用三组权重，把每个位置变成 query、key 和 value。对本例，投影后的形状是：

| 对象 | 形状 | 在后续操作中做什么 |
| --- | --- | --- |
| $Q$ | $[M,32,128]$ | 当前位置提出查询 |
| $K$ | $[M,8,128]$ | 各位置提供可匹配的特征 |
| $V$ | $[M,8,128]$ | 各位置提供被汇集的内容 |

这三个对象来自同一层输入的不同投影。例如，$W_Q$ 是 $[4096,4096]$ 的矩阵，$W_K$、$W_V$ 各为 $[4096,1024]$。前面学过的矩阵计算，在这里产生了具体的中间对象。

对位置 $i$，某个 query head 用 $q_i$ 与可见位置的 $k_j$ 做内积，经缩放和 softmax 得到权重，再把对应的 $v_j$ 加权求和。32 个 query heads 分成 8 组，每组共享一套 K、V。最后汇集各头输出，投影回隐藏维度，并继续经过残差、前馈等部分。

因果遮罩规定 $j\le i$：位置 $i$ 可以使用此前位置，不能使用未来位置。于是我们有了两种依赖：前馈块在每行内部计算，Attention 让同一条序列的不同位置交换信息；层与层又依次传递新的隐藏状态。把多条序列合成矩阵行，可以共享投影计算，但 Attention 仍要区分序列，不能让无关请求互相看到内容。用形状先确定工作，再数 FLOPs 和字节的组织方式，可参照 [Transformer Accounting](https://jax-ml.github.io/scaling-book/transformers/)；这里采用的是本笔记自己的算例。

这也补上了上一章切序列时留下的问题。若把一条长序列分给两张卡，各自的前馈计算可以处理本地行；全局 Attention 却还需要其他分块的 K、V 或相应归约结果。因此上下文并行除了分担激活，还要安排状态交换，不能只把 token 数除以卡数。[Megatron Core：Context Parallel](https://docs.nvidia.com/megatron-core/developer-guide/latest/user-guide/features/context_parallel.html)

## 长度增加，计算与中间结果怎样增长

假设本次输入包含 4096 个位置。每个 query head 都要处理当前序列中许多位置对，概念上对应一个 $4096\times4096$ 的分数矩阵；因果遮罩只保留下三角的有效关系。把长度加倍，位置对大约变成四倍，而前馈块处理的行数只变成两倍。二者的增长方式因此不同，不能只看输入 token 总数。

但“数学上存在这个矩阵”不要求实现把完整矩阵存入 HBM。FlashAttention 把 query、key、value 分块读入片上，在线更新 softmax 的归约量与输出，避免完整分数、概率矩阵反复落到显存；训练反向时重算所需中间值。它改善了执行与存储组织，仍计算精确的稠密 Attention，没有消除位置对的二次计算。这里的精确指没有换成稀疏或低秩近似，浮点归约顺序改变仍可能使结果不逐位一致。[FlashAttention（2022，论文修订 v2）](https://arxiv.org/abs/2205.14135v2)

再只改变 KV 头数。若把本例的 8 改成 32，每个位置的 K、V 各由 $8\times128$ 增至 $32\times128$ 个元素。反过来，GQA 相对这个对照减少了四分之三的 K、V 元素，但 query 仍有 32 个头，不能据此说 Attention 的所有计算都降为四分之一。共享 K、V 还涉及表达能力与训练适配，需要验证质量。后文始终使用原定的 8 个 KV heads。[GQA v3，§2](https://arxiv.org/html/2305.13245v3#S2)

到这里已经分清两类对象：完整分数矩阵是计算中的中间结果，K、V 则按位置产生。下一章将解释为什么生成时需要把后者保存下来，而不必长期保存前者。

## 想扩大前馈容量，为什么会遇到路由和通信

现在只替换刚才的前馈块。准备 $E$ 个专家，每个 token 选择 $k$ 个。若每个专家与原块同样宽，专家总参数约为原块的 $E$ 倍，每个 token 激活的前馈计算却约为 $k$ 倍。想保持相近的每 token 计算，还要调整专家规模等条件；稀疏选择本身不保证同等质量或更短时间。[Switch Transformer（JMLR 2022）](https://jmlr.org/papers/v23/21-0998.html)

当专家分布在不同 GPU 上，行也不再只留在本地：先按所选专家整理并发送 token，在目的地计算，再把结果送回组合。平均来看，每个专家接到的行数约为 $Mk/E$，实际还取决于路由。若行数很少，大矩阵权重只服务少数行，难以摊薄读取；若分配不均，有的专家排队、有的空闲。增加总容量以后，压力由此进入权重存储、负载与通信。

DeepSeek-V3 的节点受限路由把网络位置纳入选择，控制一个 token 会触及哪些节点。这是对上述问题的一种具体回答，而非所有网络上都能隐藏通信的保证。[DeepSeek-V3 报告 v2，§2.1.2](https://arxiv.org/html/2412.19437v2#S2.SS1.SSS2)

## 数据表示更小以后，执行条件也要重新计算

回到原定的 8B 稠密模型，最后只改变表示方式。基线 BF16 权重约 16 GB；若仅将权重存储字节数减半，理想存储量就降到约 8 GB。但实际执行还要读取缩放因子、转换格式，并使用合适的计算指令。更低位宽能提供多少算力，必须看对应硬件和算子，不能继续沿用另一种精度的计算预算。

数值误差也沿模型传递。DeepSeek-V3 的 FP8 训练采用细粒度缩放，处理累加精度，并保留部分组件的较高精度。这说明减少字节、得到更快的指令路径和维持训练质量，是需要分别落实的条件。[DeepSeek-V3 报告 v2，§3.3](https://arxiv.org/html/2412.19437v2#S3.SS3)

本章始终先确定对象，再改变一个条件：长度改变位置对，KV 头数改变 K、V 的大小，专家改变行的去向，精度改变字节与执行路径。混合递归层等结构还会增加需要恢复的状态，其具体案例放在 [[05 从模型权重到一次生成#从状态容量走到缓存实现|下一章的缓存恢复部分]]，等生成循环和状态寿命明确后再讨论。

接下来保持原定模型不变，让代码助手实际生成一段回答。问题不再是“这一层怎样算”，而是“为什么下一个 token 要再调用模型，哪些旧工作能够留下”。
