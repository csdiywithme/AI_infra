# 当请求变成多模态任务与 Agent

[[00 AI Infra 整体主线|整体主线]] · 上一篇：[[07 当生成结果又参与模型更新]] · 下一篇：[[09 怎样让整套系统持续交付结果]]

现在回到同一个 8B 代码助手的在线服务分支。用户给出一张报错截图，要求它查仓库、运行测试，再提出补丁。第 07 章研究反馈怎样更新模型；这里研究现有模型怎样组织多步行动，完成眼前的修复任务。任务可以做完而不更新权重，也可能以后被筛选为学习材料。

先保留[[算例与符号约定]]的文本模型。每次调用输入 4096 token、最多输出 256 token；这不是整项任务的总预算。多轮调用会重新组成上下文，额外代码和测试日志不能无上限塞进同一个输入窗口。

## 第一条新增链路：截图怎样成为模型能用的输入？

原来的文本权重不能因为请求里附了图片就自动看懂它。我们先给产品加 OCR 前端，把截图里的报错转成文字，连同用户描述组成文本输入。OCR 出错可能让后面的推理建立在错误栈上，因此要保留截图关联，并评估关键路径和错误信息是否提取正确。

另一种方案是增加视觉编码器及与语言模型匹配的连接、训练与输入处理，或者换成经过适配的视觉语言模型。这改变了模型与工作负载，必须另算编码成本、视觉序列、KV 和质量，不能继续套用原来 8B 文本模型的全部数字。Qwen2.5-VL 就是一个具体例子：不同尺寸图像和视频采样方式对应不同长度的视觉序列。[Qwen2.5-VL v1，第 2.1 节](https://arxiv.org/html/2502.13923v1)

不同多模态系统还可能使用其他表示和计算路径。因此，先沿实际输入处理链路识别工作量，再决定编码与生成是否共用资源。图片文件大小或文字 token 数都不能独自预测整条链路的成本。

## 从一句建议到一次工具执行，中间缺了什么？

先沿 OCR 路线把这一次修复任务展开：

| 当前步骤 | 交给下一步的结果 | 继续执行的条件 |
| --- | --- | --- |
| OCR 和输入整理 | 报错文字、任务与上下文 | 输入能够被文本模型消费 |
| 模型请求查仓库 | 工具名与查询参数 | 能解析成合法动作 |
| 执行器读取相关文件 | 代码片段与仓库版本 | 查询确实完成，结果可关联 |
| 模型提出补丁并请求测试 | 补丁、测试参数 | 补丁可应用，参数可校验 |
| 执行测试并回传观察 | 退出状态、日志、超时信息 | 执行结果已记录 |
| 模型修订或结束 | 新补丁或最终说明 | 达到验收标准，或预算耗尽 |

工具请求是一份待执行动作。模型输出了看似正确的 JSON，既不代表执行器已接受它，也不代表测试真的运行成功。解析失败需要重新生成或修复格式；执行超时需要记录失败；测试未通过则把具体观察交回模型。三种问题对应不同的下一步。

> [!example]- 已有案例：deepseek-recipe 处理的是协议衔接
> deepseek-recipe 将请求协议转换成 Conversation，再编码 prompt/token 并解析流式输出。它不是训练配方，也不替调用者完成模型推理、工具执行和生产 API 服务。它能生成输出约束，但后端是否真正执行约束解码仍由接入方决定。
>
> 因此，“能解析工具调用”“格式受到约束”“工具执行成功”必须分别验收。第 05 章的计算引擎与这里的协议库互补，拼接二者仍不能证明完整 Agent 任务可靠。这个固定版本案例也不表示其 DeepSeek 适配可以直接套在本章的教学模型上。[固定版本 README](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/README.md) · [输出约束代码](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/deepseek-recipe/src/protocol/output_constraint.rs) · [[来源与证据#AIINFRA-E-20261026-02|范围与示例边界]]

两次独立的文件查询可以并行，测试却要等待相应补丁落到指定代码版本。并行安排不能越过这种依赖。重试还会多花模型调用与工具时间，因此执行层需要知道剩余时间、次数和成本预算，不能每遇到失败都无限展开分支。

## 测试还在运行，GPU 和上下文该怎么办？

工具调用发出后，GPU 可以去服务其他请求，但代码修复任务尚未结束。假设有 32 个任务等待 CPU 测试，若每个都保留 4096-token 前缀，仅这些前缀的 KV 就占 32×512 MiB，约 17.18 GB；后续已生成的位置还要额外计入。它们会占用算例中仅有的 24 GB KV 预算。

这说明工具慢不仅增加任务等待，也可能挤占新请求的容量。可以保留 KV 等返回，也可以转移或回收它。512 MiB 经过 50 GB/s 链路，单次纯载荷传输约 10.7 ms；若要来回转移还应分别计账。实际选择要连同排队、加载、布局恢复和重算成本比较，不能把这一个除法当作可保证的恢复延迟。

不保留 KV 并不等于丢失任务。负责组织执行的 harness 应保存仓库版本、已应用的补丁、工具调用及其结果、下一步动作。LangGraph 的会话图状态检查点与跨会话 store，就是应用持久状态的一种组织方式。[LangGraph 持久化文档，查阅于 2026-10-22](https://docs.langchain.com/oss/python/langgraph/persistence)

KV 则是模型在特定权重和输入下的中间张量。它被回收后，可以从已记录的文本与工具结果重建上下文再计算；只有 KV，却无法判断补丁是否已经应用、测试是否已经完成。恢复时必须先核对这些动作状态，避免重复应用补丁或把旧版本上的测试当作新补丁的结果。

## 回到下一次调用，怎样保证仍在做同一件事？

测试结果到达后，harness 把必要日志和当前代码交给模型。上下文若超过 4096 token，需要检索、裁剪或摘要；这会改变模型看见的信息，应检验是否漏掉失败原因。前一轮与后一轮讨论同一个 bug，并不意味着整个 KV 都可以复用。

可复用部分需要计算等价：相同前缀、模型、适配器及相关输入条件。工具结果改变了后缀，不影响此前共同前缀的复用资格；若重排或改写了前面内容，复用边界也会移动。vLLM v0.33.0 的前缀缓存将父块哈希、当前块 token 和额外标识纳入块哈希。多模态输入的哈希属于额外标识，用于区分占位 token 相同的不同图片。[vLLM v0.33.0 前缀缓存设计](https://docs.vllm.ai/en/v0.33.0/design/prefix_caching/)

最终验收沿这条任务记录进行：补丁是否修复问题，有没有引入回归，多久完成，模型、OCR、CPU 测试和重试合计花了多少资源。首 token 很快，却长时间等测试或循环生成错误补丁，仍不算一次好的交付。缩小截图、少做校验或并行试更多补丁，都需要把质量和成本一并比较。
