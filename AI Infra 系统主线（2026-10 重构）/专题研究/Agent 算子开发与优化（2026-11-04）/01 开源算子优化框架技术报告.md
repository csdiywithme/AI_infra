# 开源算子优化 Agent 框架：搜索、测量与验收如何形成闭环

调研截止：2026-11-04，Asia/Shanghai。范围为 Atrex Kernel Agent、meta-pytorch/KernelAgent、KernelFoundry。本文使用官方仓库、固定源码和论文；未启动 GPU、未调用付费模型进行优化，所有性能结果均为作者报告。源码中的实现存在不等于在任意部署环境已验证。

## 结论与适用范围

这三个项目分别把工程重点放在不同位置：Atrex 强调谁有权接受一个优化；KernelAgent 强调如何利用硬件信号展开搜索；KernelFoundry 强调如何保持搜索多样性并把实验分配给不同工具链。它们都超出了“给模型一段 CUDA 提示词”，但都不能替代用户定义 workload、数值语义和端到端目标。

| 项目 | 最有价值的机制 | 首要适用场景 | 当前主要缺口 |
|---|---|---|---|
| Atrex Light | 源码封存、私有测量、独立晋升 | 长时运行、多文件、远程 GPU 的工程型优化 | 默认隔离是协作约束；若干回归只给出作者临时 fixture，部署依赖需实测 |
| KernelAgent | 硬件诊断、beam、多模型/PTX 去重 | 从 PyTorch 生成 Triton，或改进已有 Triton | 通用验证路径仍需加强；源码和性能报告并非同一版本 |
| KernelFoundry | MAP-Elites、参数搜索、MCP/任务打包 | Intel/SYCL、跨工具链自动实验 | 公布结果的比较层级与聚合口径需认真核对 |

- Atrex：[`02ff86be4cd7467c28fdaaa7d3bc71f1b107ca48`](https://github.com/alibaba/atrex-kernel-agent/commit/02ff86be4cd7467c28fdaaa7d3bc71f1b107ca48)，提交时间 2026-11-02。
- KernelAgent：[`e0647170da36ef9b059ac0bd3d60103aa4ed378b`](https://github.com/meta-pytorch/KernelAgent/commit/e0647170da36ef9b059ac0bd3d60103aa4ed378b)，提交时间 2026-07-15。

## 1. Atrex：把候选生成和接受候选分开

### 从一次修改到一次可接受的实验

Atrex Light 的主线可以概括为：

`固定任务 → 管理候选草稿 → Runtime 冻结源码并测量 → agent 提交记录 ID → 独立正确性验收 → 封存源码 → ABBA → 晋升或保留原版`。

agent 编辑的是 Git-free draft；Supervisor 控制真实 Git、evaluator、测量账本和晋升审计。报告中写“已经通过”不产生接受权限；必须能找回绑定精确候选的记录。多文件候选的身份覆盖头文件、构建设置、文件删除，而不只看 kernel.py。报告完成后的草稿修改不会更改已封存候选。这直接处理了“测量后又改了一行”“编译参数不同”“agent 引用旧日志”这类常见问题。[晋升契约](https://github.com/alibaba/atrex-kernel-agent/blob/02ff86be4cd7467c28fdaaa7d3bc71f1b107ca48/docs/supervisor-promotion.md)

Runtime 为任务计算身份，身份包含源码、evaluator/input bytes、操作、目标执行设置和重复策略。重复请求通常返回已有记录，已接受的远程作业按 ID 恢复；不知道提交是否成功时不能盲目再交一次。这既节约计算，也避免搜索器反复抽样直到偶然出现有利结果。[测量和恢复](https://github.com/alibaba/atrex-kernel-agent/blob/02ff86be4cd7467c28fdaaa7d3bc71f1b107ca48/docs/measurement-records.md)

### 正确性与性能门槛

源代码确认，Atrex-Bench 的候选验收会检查基础 case 加另外五个 seed；SOL 则使用对应完整 workload gate。错误、缺失或自相矛盾的结果不能成为成功证据。额外 production numerical probes 是独立机制，不能将“六个 seed”解释为浮点语义已经穷尽。[acceptance/provider.py](https://github.com/alibaba/atrex-kernel-agent/blob/02ff86be4cd7467c28fdaaa7d3bc71f1b107ca48/src/aka/light/acceptance/provider.py)

Light 的性能 gate 实际检查完整 ABBA 日程与全部有效结果，再计算：

`improvement_pct = 100 × (incumbent_latency − candidate_latency) / incumbent_latency`

候选晋升先通过覆盖完整 shape 集合的六 case 数值检查（base seed 加五个额外 seed）；随后 Supervisor 的 retention ABBA 请求对每个 shape 使用一个 correctness case 做配对性能比较。六 case 数值检查与 ABBA 重复次数是两套设置，不表示六 seed 的性能都参与 ABBA。这里两边使用几何平均延迟，严格大于配置阈值才通过；reference-relative performance_score 仅用于诊断，不决定晋升。ABBA 可减轻随时间漂移，但本实现不是置信区间检验，也不能消除缓存顺序效应。对微小收益仍应在独立会话中复测。[verifier.py](https://github.com/alibaba/atrex-kernel-agent/blob/02ff86be4cd7467c28fdaaa7d3bc71f1b107ca48/src/aka/light/acceptance/verifier.py)

### 隔离和恢复的真实边界

默认 native Light 是同 UID 的协作式分离；Linux 的 light-sandbox 通过 Bubblewrap 强制文件可见范围，但文档明确说这并不增加网络隔离。这里不能把“Supervisor 私有”直接等同恶意代码安全边界。Profile/Dev 结果也不自动成为验收证据，源码绑定的 Dev record 不能证明用户命令实际测了该源码。[Runtime](https://github.com/alibaba/atrex-kernel-agent/blob/02ff86be4cd7467c28fdaaa7d3bc71f1b107ca48/docs/supervisor-runtime.md)

这套所有权设计比多 agent 角色命名更有复用价值。不过维护文档承认部分集成与回归验证依赖作者机器 /private/tmp 下的临时 fixtures；此次树检查未找到顶层 tests/。文档报告的通过数量无法由公开 checkout 原样复跑，生产 GPU 与真实 provider 的 rollout smoke 仍要求部署者完成。**工程契约丰富，公开可复现验证尚不等量充分。**[验证范围](https://github.com/alibaba/atrex-kernel-agent/blob/02ff86be4cd7467c28fdaaa7d3bc71f1b107ca48/docs/optional-light-modules.md)

### 采用方式

适合将自己的算子接成 evaluator-owned task，再选择源码 layout 和 GPU execution provider。第一次仅跑一项已有 reference 的任务，验证“候选变更确实产生新身份、错误结果不晋升、中断恢复不重复交作业”后，再开长时搜索。依赖包括 coding-agent backend、工具链、真实 evaluator 和可访问 GPU；Light 的 native ABBA 依赖 Agate Atrex-Bench，不能想当然换成任意 SSH 脚本。

上轮关于 Atrex 的推荐仍成立，但应限定为**优先研究其验收架构**，而不是已证明最成熟或最快。README 中三个算子家族、60 shapes、最高 1.55× 的数据是作者生产案例；本轮未核到完整原始测量包，不据此给框架排名。[README](https://github.com/alibaba/atrex-kernel-agent/blob/02ff86be4cd7467c28fdaaa7d3bc71f1b107ca48/README.md)

## 2. KernelAgent：从硬件诊断到有界搜索

### 生成与优化是两条相连的链

生成链先把 PyTorch 问题拆成可融合子图，分别生成 Triton，验证后组合回原 forward。优化链接收已存在的 Triton，组织 profile、诊断、修改、验证和计时。组合结果可以仍包含多个 kernel，不能把“端到端 Triton 程序”称为 megakernel。[README](https://github.com/meta-pytorch/KernelAgent/blob/e0647170da36ef9b059ac0bd3d60103aa4ed378b/README.md)

一个 worker 内的 OptimizationOrchestrator 保存 OptimizationAttempt 和 Reflexion：修改假设、是否通过验证、实际结果、下一步避免什么。代码确有验证失败后的 refine 路径、best-runtime 候选保留、最终重做 profile。它提供的是把硬件证据转成下一轮搜索建议的骨架；LLM 的解释仍是待验证假设，不是由计数器自动推导的因果证明。[orchestrator](https://github.com/meta-pytorch/KernelAgent/blob/e0647170da36ef9b059ac0bd3d60103aa4ed378b/triton_kernel_agent/opt_worker_component/orchestrator/optimization_orchestrator.py)

### Beam 的扩展成本和去重

当前 BeamSearchStrategy 允许同时展开 P 个父候选、M 个瓶颈方向、K 个模型、C 次独立采样，单轮潜在 worker 数为 `P×M×K×C`。返回成功候选后，与旧 beam 合并，按编译后的标准化 PTX 指纹去重，再按 runtime 取前 N。无 PTX hash 的候选不会互相误合并。这避免把只是变量名、注释不同的代码当成新设计；也意味着“多 agent”可能只是更多相同实验，去重必须发生在编译层。[beam_search.py](https://github.com/meta-pytorch/KernelAgent/blob/e0647170da36ef9b059ac0bd3d60103aa4ed378b/triton_kernel_agent/opt_worker_component/searching/strategy/beam_search.py)

最新提交还加入 per-GPU lock、父候选 NCU 缓存和多 GPU worker 分配；benchmark 与 NCU 共用相应 GPU 锁，减少并发污染。并行主要隐藏模型与编译等待，单 GPU 上计时仍须串行。PTX 去重不能证明不同 PTX 行为不同，也不能取代语义测试。[提交说明](https://github.com/meta-pytorch/KernelAgent/commit/e0647170da36ef9b059ac0bd3d60103aa4ed378b)

### 测量路径存在必须读源码的细节

Benchmark 包装器提供子进程 crash protection 和 300 秒超时；candidate benchmark 本身明确假定正确性已在上游验证。因此只拿 benchmark 文件当独立评测器会漏掉正确性门槛。[benchmark.py](https://github.com/meta-pytorch/KernelAgent/blob/e0647170da36ef9b059ac0bd3d60103aa4ed378b/triton_kernel_agent/opt_worker_component/benchmarking/benchmark.py)、[kernel_subprocess.py](https://github.com/meta-pytorch/KernelAgent/blob/e0647170da36ef9b059ac0bd3d60103aa4ed378b/triton_kernel_agent/opt_worker_component/benchmarking/kernel_subprocess.py)

默认 do_bench 路径将 warmup=25、rep=100 传入 Triton，含义是毫秒预算，而不是固定 25/100 次；输出字符串却写成“mean over 100 runs”，不能据日志字面重建协议。该 subprocess 还会根据候选源码包含 bfloat16/float16/half/float32 自动选择 dtype。**生产采用时应从不可变任务定义传 dtype，禁止候选文本影响输入精度。**这是静态风险发现，尚未构造 GPU 反例验证可利用性。[计时工具](https://github.com/meta-pytorch/KernelAgent/blob/e0647170da36ef9b059ac0bd3d60103aa4ed378b/triton_kernel_agent/opt_worker_component/benchmarking/timing.py)、[候选计时入口](https://github.com/meta-pytorch/KernelAgent/blob/e0647170da36ef9b059ac0bd3d60103aa4ed378b/triton_kernel_agent/opt_worker_component/benchmarking/kernel_subprocess.py)

Fuser runner 有子进程超时、日志上限和 Python socket 屏蔽，但这不是操作系统级完整沙箱。Beam 外层 should_terminate 仅检查 max_rounds；worker 内另有 roofline 停止逻辑，不能说整个搜索都在95% SOL后停止。[runner.py](https://github.com/meta-pytorch/KernelAgent/blob/e0647170da36ef9b059ac0bd3d60103aa4ed378b/Fuser/runner.py)、[Beam停止规则](https://github.com/meta-pytorch/KernelAgent/blob/e0647170da36ef9b059ac0bd3d60103aa4ed378b/triton_kernel_agent/opt_worker_component/searching/strategy/beam_search.py)

### 结果能证明什么

2026-03 的 PyTorch 文章报告 H100、100 个 KernelBench L1任务，相对旧正确性版几何均值2.02×、相对默认 torch.compile 1.56×，65题更快；后者限定静态shape、CUDA Graph关闭。89%指标是 compute/memory SOL 的较大值，不是算术强度 roofline 距离，也不是89%的端到端硬件效率。它与此次7月源码快照不是同一次实验版本。[官方实验说明](https://pytorch.org/blog/kernelagent-hardware-guided-gpu-kernel-optimization-via-multi-agent-orchestration/)

适合从现有 matvec/RMSNorm example 开始，固定1模型、1父候选、1瓶颈和小轮数，随后再放大beam。外推生产前应换成固定 evaluator、额外随机分布、held-out shapes、相同精度与Graph条件，并重新测最终源码。预算可先估算 `轮数×P×M×K×C×每候选模型/编译/验证/profile成本`；增加 GPU 不会减少总 GPU秒或模型token。

## 3. KernelFoundry：用搜索档案保持多条优化路线

### 为什么不是只保存全局最快版

KernelFoundry将可编辑代码限制在EVOLVE区域，reference、build、pytest correctness/performance测试和配置组成task package。AnswerProcessor只提取允许改写的块；这提供程序性约束，但如果外部 coding agent 也能改task package，仍需冻结输入，不能把标记当安全隔离。[answer_processor.py](https://github.com/isl-org/kernelfoundry/blob/93ee9227068a9fed379c0e3bff9a7570a87b77db/kernelfoundry/algorithm/answer_processor.py)

其 OptimizationAwareDatabase 当前实现配置为四维、每维四级，共 256 格的 MAP-Elites 档案，按 memory、compute、parallelism、esimd 代码模式分桶。CUDA、Triton、OpenCL 的 ESIMD 维固定为 0，因此实际使用 64 格切片。论文方法段和类注释仍描述三维 64 格，论文 Table 6 则写四维，存在内部不一致；不能仅凭注释判定实现维数。每格保留高分候选。这样某条当前稍慢但不同的设计不必立刻被全局top-k淘汰。坐标由静态模式匹配而非硬件测量产生；“检测到共享内存”并不证明存在有效数据复用，搜索的多样性是语法代理而非语义保证。[database](https://github.com/isl-org/kernelfoundry/blob/93ee9227068a9fed379c0e3bff9a7570a87b77db/kernelfoundry/algorithm/evolve_database_optimization_aware.py)

TransitionTracker记录父子格子、收益和时间，估计有利迁移方向；这不是对程序可微求导。另有prompt evolution和模板参数搜索。当前 AgenticController 还可根据选中父候选fork其agent会话，并发运行配置数量的branch，把结果加入档案；必须区分论文经典进化路径与MCP/coding-agent工作流，二者并非一次完整重跑已证明等效。[qd_gradient.py](https://github.com/isl-org/kernelfoundry/blob/93ee9227068a9fed379c0e3bff9a7570a87b77db/kernelfoundry/algorithm/qd_gradient.py)、[controller](https://github.com/isl-org/kernelfoundry/blob/93ee9227068a9fed379c0e3bff9a7570a87b77db/kernelfoundry/algorithm/agentic_controller.py)

### 工具链、测试和可观察性

TaskRunner分离build与test，可本地执行或提交Celery队列；测试流程先 correctness，失败则跳过后面的profiling，再独立运行性能和profiler子进程。MCP负责打包、提交、轮询和回填EVOLVE代码。公开tests至少覆盖编译错误诚实呈现、profiler输出、MCP配置和CLI代理等边界，但不能把这些单元测试等同GPU正确性验证。[TaskRunner](https://github.com/isl-org/kernelfoundry/blob/93ee9227068a9fed379c0e3bff9a7570a87b77db/kernelfoundry/eval_pipeline/tasks/task_runner.py)、[测试流水线](https://github.com/isl-org/kernelfoundry/blob/93ee9227068a9fed379c0e3bff9a7570a87b77db/kernelfoundry/eval_pipeline/tasks/test_custom_task.py)、[MCP](https://github.com/isl-org/kernelfoundry/blob/93ee9227068a9fed379c0e3bff9a7570a87b77db/kernelfoundry/mcp_server/server.py)、[错误呈现测试](https://github.com/isl-org/kernelfoundry/blob/93ee9227068a9fed379c0e3bff9a7570a87b77db/tests/test_compile_error_honesty.py)

### 必须修正上轮引用的2.3×

README写“2.3× geometric mean”，但论文v1 Table2的111个过滤后SYCL任务列为 **算术均值2.32×、几何均值1.38×，正确率97%**。本文优先采用表格并保留冲突；不得把2.3×继续写成几何均值。论文主要硬件为Intel Arc140V/B580，CUDA对比在RTX A6000，基线通常为PyTorch eager。[README](https://github.com/isl-org/kernelfoundry/blob/93ee9227068a9fed379c0e3bff9a7570a87b77db/README.md)、[论文Table2](https://arxiv.org/html/2603.12440v1#S5.T2)

论文还明说robust-kbench backward对候选测isolated kernel，但reference仍测torch.autograd.grad，扩大了speedup。这种“应用路径缩短”可有实用价值，却不能全部归因于kernel本身。它的1%相对误差覆盖99%元素等数值策略也不是用户可直接沿用的通用标准。[论文实验协议与附录B](https://arxiv.org/html/2603.12440v1#A2.SS2)

适合Intel/SYCL或想系统比较搜索策略的使用者。NVIDIA用户可复用task/MCP框架，但应从CUDA task独立验证；不要把Intel路径成绩当Blackwell成绩。初次只接一个task，先确认reference可靠、build和profiler权限正常，再配置搜索。40轮×8候选已是数百次编译评测，不能把论文“轮数”当模型调用次数。

## 4. 如何选择与如何做公平试验

建议先按自己的工作负载选择：已有Triton且想研究诊断和搜索，选KernelAgent；需要长时任务管理和严格证据晋升，研究Atrex；以SYCL、跨后端或quality-diversity为主题，选KernelFoundry。不要仅按作者平均speedup排名。

用于比较三者的最小实验应当固定同一模型、token/GPU预算、源码版本、GPU/driver/工具链，选择至少三类任务：带宽型RMSNorm、规约型softmax、包含张量核/异步流水的GEMM或attention子任务；每类含开发shape和未见shape。分别报告正确率、正确且快的比例、几何平均收益、最差退化、总GPU秒、token与人工介入次数。最终再回到实际forward或服务，验证收益能否传递。

最值得借鉴的共同原则是：**agent可以自由提出方案，评价标准、测量身份和接受条件必须稳定。** 算子工程的关键仍在任务定义、反例、数值边界和性能判断。

## 5. 尚未完成的验证

- 未在GPU重跑任何作者结果，未验证远程provider可用性或当前费用。
- Atrex生产案例完整原始数据与公开回归fixtures的覆盖不足；native/Legacy和具体source layout需在部署时锁定。
- KernelAgent未做候选影响dtype的攻击演示，未证明其沙箱抵御不可信原生代码。
- KernelFoundry的README/论文聚合冲突待维护者解释；论文v1并非v0.5.0全套MCP路径的性能验收。
- 相关新项目KernelOPT、Kernel Forge、KernelBrain仅作独立发现候选，未完成源码审计，不纳入本报告成熟度比较。
