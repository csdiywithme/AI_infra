# Agent 算子开发与优化技术报告

Agent 写算子已经出现可复用的工程闭环，但不同项目成熟在不同位置：有的擅长生成代码，有的擅长搜索，有的擅长控制测量和验收。复杂 megakernel 仍需要人明确同步不变量、任务图和资源约束。选择方案时，应先看真实工作负载与可验证的执行链，再看作者速度数字。

这组报告按四个方向分别展开，并提供共同评测附录。研究日期为 **2026-11-04，Asia/Shanghai**。适合用于选择要复现的项目、搭建自己的工作流，以及判断哪些技术值得继续研究。

## 各方向的技术判断

**开源框架应按机制拆解。** Atrex 值得优先研究源码封存与独立晋升；KernelAgent 值得研究硬件诊断、beam 扩展、PTX 去重与预算；KernelFoundry 值得研究质量多样性搜索与跨后端任务打包。任何一个都不能仅凭作者平均加速被称为普适的成熟生产优化器。详细实现入口与固定 commit 见 01。

**专用模型的价值取决于任务量与可靠反馈。** Kevin 有开放权重，适合做专用模型对照；CUDA Agent 已公开数据、skill 和工作目录，但未形成可从公开仓库重建的完整训练链。个人起点可以是冻结强模型加现有 evaluator，再测记忆和搜索的增益；已有稳定大量任务时再考虑训练。开放边界与奖励设计见 02。

**Megakernel 的研究重心是调度与正确性。** Hazy 适合学习跨任务流水线；当前 Mirage 不仅有旧动态 runtime，也包含静态计划、代价驱动搜索和检查器；AMK 的受约束编辑面值得参考，但静态覆盖和同步实现仍需补强。MoK 提供了专家与 agent 共同交付复杂系统的案例，尚未提供 agent 独立设计能力的受控对照。具体代码与比较条件见 03。

**Codex 已经能接现成工具，不必先造完整平台。** 官方 NVIDIA Skills 中的 TileGym 是上一轮遗漏的重要来源；对已有 CUDA/Triton 项目，优先复用自己的测试和 benchmark，再接文档/NCU 组件。Skill 管理流程，工具执行约束，evaluator 决定接受结果，这三者应清楚分工。实现建议见 04。

## 实际研究范围与证据强度

初筛使用问题检索，随后对代表项目读取官方仓库、论文和固定版本核心代码。新发现包括 NVIDIA TileGym Skills、OpenEnv KernRL，以及 CUDA-L1 的当前发布入口。KernelOPT、Kernel Forge、KernelPro、Cohere megakernel 与 mKernel 等只作补漏候选或文档级对照，未全部完成源码审计，不进入已验证能力排名。这不是全领域或全部新提交的完整枚举。

证据分四类：维护者文档说明、作者实验结果、固定源码审阅、本轮本地实验。代码存在只支持机制判断；作者生产案例不等于独立复现。性能数字在相应段落保留硬件、精度、baseline、任务集合和版本条件。

本轮真正执行的只有 **CPU 格式 gate 反例与文档结构检查**。未运行 GPU、训练模型、复现作者加速、安装插件、认证外部 MCP 或提交付费作业。因此可以据报告决定复现顺序，不能将其当作 B300 上的性能验收。

来源记录保存在 [框架来源](evidence/frameworks-sources.json)、[学习方法来源](evidence/learning-sources.json)、[megakernel 来源](evidence/megakernel-sources.json)、[工具链与评测来源](evidence/toolchain-evaluation-sources.json)。它们记录 URL、版本、所支持的结论和证据类型；引用网页仍可能后续更新，关键源码链接已固定到 commit。

## 建议先做的一个实验

选择一个已有可靠 baseline 的真实算子：例如有多 shape 的 RMSNorm、softmax，或当前熟悉的 GEMM/attention 子任务。先固定硬件、数值契约、真实输入分布和预算，再比较普通 agent、加诊断/知识、加受控搜索三组。保留所有失败与回退，最终候选在独立 workload 上重测。

若这一步已经能稳定产生正确且有效的改进，再引入更复杂的搜索或 megakernel。这样能把个人贡献落在可检查的地方：发现何种瓶颈、如何收紧候选空间、排除了什么假加速、最终收益在哪些条件下成立。
