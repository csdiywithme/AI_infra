# 算子 Agent 技术报告二：专用模型、强化学习、搜索与经验记忆

**结论：短期使用价值最大的是把强模型接到可信的实验环境；训练专用模型适合已有大量、重复、可验证任务的团队。** Kevin 证明多轮反馈可以成为训练对象；CUDA Agent 把它扩大成终端工具使用和长轨迹训练；KernelEvolve、KernelClaw 则说明不更新权重也能靠搜索、硬件知识和历史记录改善结果。这四条路线可以组合，却不能用一张 benchmark 排行榜替代选型。

调研截止 2026-11-04。证据标记为 **[论文]**、**[代码]**、**[模型/数据实物]**、**[分析]**；前三者都是本轮读取的公开一手资料，并非独立 GPU 复现。本轮没有启动模型服务、运行 GPU benchmark 或训练。下文中的“未发现”只针对列出的官方发布入口，不表示互联网上不存在其他实现。

## 1. 先分清楚：学习发生在哪里

| 路线 | 改变的状态 | 一次新任务的主要成本 | 代表工作 |
|---|---|---|---|
| Test-time refinement/search | 当前候选、搜索树、反馈上下文 | LLM 调用、编译、GPU 评测 | KernelEvolve |
| 检索与经验记忆 | 外部知识库、失败轨迹、方法标签 | 检索、整理和读取上下文 | KernelClaw/KernelMem |
| 多轮 RL | 模型权重及其迭代策略 | 离线训练；使用时仍需评测 | Kevin、CUDA Agent |
| 对比式训练 | 权重，以及带分数的代码样例库 | 样例生成、验证、RL | CUDA-L1 |

**[分析]** “自动迭代 100 次”本身不等于 RL。一个冻结模型在 100 次实验里找到更好的实现，是搜索；把这些轨迹用于梯度更新，才是参数学习。把经验写入 skill 或数据库，是外部记忆。工程上应分别测量候选质量、反馈利用效率和历史知识迁移，不能统称为“自进化”后只报告最终最快值。

一个可比较的环境可以写为：状态是任务定义、候选源码、已有测量和剩余预算；动作是改代码或调用工具；观测是编译日志、数值误差、独立时延和 profiler 指标；终止条件是达到收益门槛、预算耗尽或连续无改善。环境的正确性决定了训练目标是否有意义。

## 2. Kevin：把“根据反馈修正”训练进模型

**[论文]** Kevin 使用 QwQ-32B，多轮训练中每一轮都接收执行反馈。其核心得分为

$$
S=\mathbf 1_{correct}\left(0.3+T_{eager}/T_{candidate}\right)
$$

早期动作还要承担其后续改进的信用；论文使用折扣后的后续分数，实验中 `gamma=0.4` 的求和方案较好。上下文压缩保留代码和总结，避免每轮推理文本无限增长。固定 128 次生成预算时，`16 条轨迹×8 轮` 比 `128×1` 更有利：其表中速度分数分别是 1.10×、0.65×。这些是对应任务划分和搜索预算下、相对 eager 的结果。[Kevin arXiv v1，第 3–5 节](https://arxiv.org/html/2507.11948v1)

**[分析]** 这解决的是“第一次写错并不一定是坏策略”：有些错误尝试会揭示布局或数值问题，帮助之后产生优解。只奖励最后一轮会丢掉中间动作差异；只奖励当轮会压制有潜力的探索。折扣回报是两者之间的选择。不过速度比没有上界，极端易优化任务可能主导梯度，换到另一组任务时需重做奖励校准。

**[模型实物]** 官方 HF 仓库确有权重：读取时 revision 短哈希 `7264025`，29 个 safetensors 分片，页面显示约 131 GB、F32。它是可下载专用模型，而非仅有论文。完整训练代码和与论文逐项对应的数据划分，在这次核查的模型卡中未建立发布入口。[Kevin-32B 权重文件](https://huggingface.co/cognition-ai/Kevin-32B/tree/7264025)

**[分析]** 下载 32B 模型不代表获得低成本优化系统：还需要构造提示、可靠编译与测试、候选选择、GPU 独占计时。转换 BF16 后仅权重规模约 64 GB 的估计也不包括 KV cache、运行时和训练状态。论文博客与 arXiv 的评测口径不同，不能把博客中的 89% 解题率与论文中的 82% 混成单一结果。[早期官方博客](https://cognition.com/blog/kevin-32b)

## 3. CUDA Agent：从固定改写轮次扩展到长轨迹工具使用

**[论文]** CUDA Agent 的流水线是单轮 RL warm-up → 轨迹 RFT 初始化 actor → value pretraining → agentic PPO。它基于 Seed1.6（230B 总参数、23B 激活），训练最多 150 agent turns、评估最多 200 turns；GPU 环境描述为 128 张 H20 的独占评测池。奖励使用里程碑而非无限放大的原始速度比：错误为 -1，正确为 1，超过 eager 5% 为 2，同时超过 eager 和 compile 5% 为 3。论文报告 L1/L2/L3 相对 compile 的 faster rate 为 100%/100%/92%；速度几何平均只统计正确解，并取轨迹最佳候选。[CUDA Agent v1，第 3–4 节](https://arxiv.org/pdf/2602.24286v1)

**[分析]** 里程碑奖励压缩了离群值影响，也使“已正确、尚不够快”的状态仍有学习信号。代价是同一档内的小幅提升没有区分度。RFT 给策略一个可执行的初始行为，critic warm-up 帮助判断长期工具调用是否值得继续；这比直接给模型一个“写快点”的分数更接近训练一个实验员。上述资源是论文系统规模，不是个人复现所需的最小配置，更不是本轮已运行的配置。

**[数据实物]** `CUDA-Agent-Ops-6K` 当前可读取 6,000 条 PyTorch 任务，字段含 `ops`、`data_source`、`code`；这是训练问题数据，不应误称为 6,000 条专家 CUDA 答案或完整成功轨迹。[官方数据集](https://huggingface.co/datasets/BytedTsinghua-SIA/CUDA-Agent-Ops-6K)

**[代码]** 仓库固定在 [`473025c8af7878e928525138b5cb327d6bcdf9dd`](https://github.com/BytedTsinghua-SIA/CUDA-Agent/tree/473025c8af7878e928525138b5cb327d6bcdf9dd)。递归树只有 README、assets 与 `agent_workdir`，能确认编译、验证、profiling 示例；未见完整 PPO trainer、训练集群调度器或模型权重入口。因此适合复用环境思想，尚不能按“开源整套训练系统”评估。

源码有两个需要在工程接入时补强的点：[`verification.py`](https://github.com/BytedTsinghua-SIA/CUDA-Agent/blob/473025c8af7878e928525138b5cb327d6bcdf9dd/agent_workdir/utils/verification.py) 默认做 5 次检查，`atol=rtol=1e-2`，并在候选 forward 内屏蔽 `torch.nn.functional`；这不是覆盖所有绕过方式的完整隔离。 [`profiling.py`](https://github.com/BytedTsinghua-SIA/CUDA-Agent/blob/473025c8af7878e928525138b5cb327d6bcdf9dd/agent_workdir/utils/profiling.py) 汇总 `torch.profiler` 中 CUDA event 的 device time，默认 warmup=5、iters=10；这类累计活动时间不能直接当无 profiler 的完整调用时延，遇到并发重叠还可能不同于 makespan。

## 4. KernelEvolve：更值得借鉴的是实验基础设施

**[论文]** 核查版本为 arXiv `2512.23236v4`。候选构成图节点，边代表一次变换；系统组合选择策略、上下文生成、变换与验收，可用 greedy/MCTS/evolution。元数据保存分数、父子关系和错误状态，内容存储保存代码，知识库保存硬件资料；硬件 interpreter 执行数值与性能检查。fitness 对编译、执行、数值失败置零。它把历史搜索恢复和跨平台知识注入作为系统的一部分。[KernelEvolve v4，第 3 节](https://arxiv.org/html/2512.23236v4)

Meta 的生产案例和吞吐提升是作者报告；公开博客也讨论了把轨迹用于专用模型训练的方向，但没有因此提供可下载的完整 KernelEvolve 平台。应把“生产部署证据较强”和“外部团队可独立复现”分开。[Meta 官方工程文章](https://engineering.fb.com/2026/04/02/developer-tools/kernelevolve-how-metas-ranking-engineer-agent-optimizes-ai-infrastructure/)

**[分析]** 对个人项目最可迁移的是：把一次优化变成持久化实验图，允许回到另一个父候选，保留失败条件，并将测量和源码绑定。MCTS 的名字本身价值有限；如果候选生成器每次输出同一种错误，搜索树再大也没有有效分支。先提升上下文与变换质量，再比较树策略，通常更容易解释结果。对于新硬件，知识库应记录“适用架构、指令、版本和反例”，而不仅是成功技巧。

## 5. KernelClaw / KernelMem：记忆改善试错，但论文数字需要审计

**[论文]** 原 KernelSkill 已于 `2603.10085v2`（2026-10-18）更名 KernelClaw。长期记忆组织优化方法，短期记忆记录计划、代码、错误与测量；主实验为 A100-80GB、KernelBench v0.1、3 seeds 后选最佳、最多 15 轮、GPT-5.1。重要的是作者审计剔除了两个异常高加速案例，修正后 L1/L2/L3 平均 speedup 为 **3.47×/3.92×/1.94×**，相对 Torch eager。原摘要仍展示 6.98×/7.89×/1.94×，不能直接作为选型成绩。[v2 第 5 节与附录 Q](https://arxiv.org/html/2603.10085v2)

**[代码]** 作者论文链接指向 `0satan0/KernelMem`，核查 HEAD 为 [`8b57ccc9adc2ae2f11fc487fd458a7ecc1ea014d`](https://github.com/0satan0/KernelMem/tree/8b57ccc9adc2ae2f11fc487fd458a7ecc1ea014d)（2026-02-14），未建立与十月 v2 的逐项对应版本。`main_memory_latest.py` 确有 repair/optimization 分流、历史上下文、NCU 调用和候选记录；其默认 10 轮，与论文 15 轮不同，复现时需要显式配置。[主循环](https://github.com/0satan0/KernelMem/blob/8b57ccc9adc2ae2f11fc487fd458a7ecc1ea014d/main_memory_latest.py)

**[分析]** 这类方法最该测试的是“相同错误是否减少”和“留给真正性能优化的轮次是否增加”，而不仅是最终 fastest。知识库也可能带来负迁移：在 A100 有利的布局、在 B300 上可能限制新指令和调度。每条经验应带触发证据和失效条件；历史应保留原始 artifact，不能仅存模型对成功原因的解释。

## 6. 独立补充：CUDA-L1 与可直接改造的 KernRL 环境

**[论文/代码]** CUDA-L1 当前论文为 v12（2026-08-05），官方仓库已由 DeepReinforce 跳转至 Ornith。它把成功实现分桶，采样性能不同的代码，要求模型比较差异并提出实现；公开仓库 [`51e8356bf844101cab2aeeca4bdff47ebb1953b8`](https://github.com/ornith-ai/CUDA-L1/tree/51e8356bf844101cab2aeeca4bdff47ebb1953b8) 提供生成 kernels 和评测脚本，未见完整训练权重与 trainer。更适合审计案例和对比式数据构造。[CUDA-L1 v12](https://arxiv.org/html/2507.14111v12)

**[分析]** 一个可用于练习论文审读的细节：其采样式 `softmax((score_i-mu)/tau)` 中减去统一常数 `mu` 不改变精确算术下的概率；它可以改善数值计算，却不能单独解释探索分布变化。复现时应区分真正改变分布的分桶、温度和采样约束，与只改变表达形式的变换。

**[代码/文档]** 新发现 OpenEnv 的 `kernrl` 提供 reset/step/state 接口和 CUDA/Triton 候选环境；当前读取 commit 为 [`f6c004341cd82ccc488fb6fde14b575ae212caa2`](https://github.com/openenv/OpenEnv/tree/f6c004341cd82ccc488fb6fde14b575ae212caa2/envs/kernrl)。奖励对编译失败、错误、正确但慢分别处理，正确且快的奖励封顶；代码中的 solved 门槛为 `speedup>1.05`。它是环境部件，不是已证明优于其他模型的 optimizer。[环境代码](https://github.com/openenv/OpenEnv/blob/f6c004341cd82ccc488fb6fde14b575ae212caa2/envs/kernrl/server/kernrl_environment.py)；[v0.9.0 文档](https://huggingface.co/docs/openenv/v0.9.0/environments/kernrl)

## 7. 怎样做可解释的研究与复现

**[分析]** 建议从冻结基础模型的对照实验开始：相同 GPU、DSL、任务、候选数量、可见文档与时限下，比较无记忆、失败轨迹记忆、带条件的专家知识三种配置。按算子族划分任务与 held-out shapes，不能把同一家族相邻 shape 分到训练和测试两边后声称强泛化。

验收应有三层：可见测试支持迭代；隐藏测试检验非整齐尺寸、stride、长尾数值分布、非默认 stream；最后接回实际模型检查误差与端到端收益。随机大矩阵的平均值容易掩盖少算行、少算元素；候选即便通过 allclose，也要核对索引、归约域和状态更新。将优化对象限定为 forward，也不能推断 backward 或长期训练稳定性。

至少报告：正确且有效率、失败计为零的总体表现、成功子集的几何平均、最差 shape 回退、总生成 tokens、编译/GPU 秒、首次可用解时间，以及最终采用解重测结果。不能从 success-only speedup 推导所有任务的收益，也不能用 best-of-200 与另一个方法 pass@1 比较。

成本模型可先写成 `训练成本/预计复用任务数 + 每任务推理与实验成本`。任务量小、硬件还在变时，先做可信环境与检索通常更划算；若有稳定的大批真实任务、足量可靠轨迹、同一硬件和反复调用需求，再考虑 SFT/RL。最合理的小规模起点是 **KernRL/现有 harness＋冻结强模型＋可审计知识库**；Kevin 可作为开放专用权重对照；CUDA Agent 先复用数据和环境，不宣称完整复现其训练。
