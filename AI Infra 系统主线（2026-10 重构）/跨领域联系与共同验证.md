# 跨领域联系与共同验证

入口：[[领域地图与覆盖缺口]]。领域综述解释各自的问题与路线，本篇解释一个选择怎样改变其他领域的约束。下面是机制推导与研究联系，不是已经完成的端到端性能实验。

## MoE：计算变稀疏后，工作怎样到达专家

若一次有 $M$ 个 token、每个选择 $k$ 个专家，共有 $E$ 个专家，均衡情况下每专家约接到 $Mk/E$ 行。增加专家容量而不增加活跃 token，可能让每个 GEMM 更小。于是 [[D04 模型结构与数值表示]] 的参数容量选择，会改变 [[D08 算子与 GPU 执行]] 的权重复用与执行效率。

这些行还需要按专家目的地重排、发送、计算，再组合返回。[[D10 通信与互联]] 不仅要搬够字节，还要使计算端知道哪些块已经就绪。通信占用的 SM、缓冲和同步又可能与专家算子争用。逐块交接可以让下游早开工，但要求布局、完成与回收条件彼此匹配。

最后，专家热点可能使部分卡排队。模型路由、专家放置/复制和集群资源分配都能改变热点，各有模型质量、容量、更新与传输成本。这条链需要模型、kernel、通信和 [[D12 集群资源可靠性与隔离]] 共同判断，不能由一个 All-to-All 带宽或 grouped GEMM 数字推导完整收益。

## 长上下文：少保存、少搬运和少重算是三种不同变化

[[D06 KV 与模型状态系统]] 中，改变状态结构或位宽可以减少逻辑字节；分页主要减少分配浪费，前缀复用主要减少重复输入计算，分层扩大可驻留范围。它们解决不同问题，也可以组合。

逻辑容量下降以后，[[D08 算子与 GPU 执行]] 还要高效读取与解码这种状态。访问更不规则、额外转换更多，可能让字节收益不能同比成为时间收益。把状态移到 [[D11 存储与异构内存]]，又要比较读取、写入、预取、淘汰和重算；不是空间更大就一定更快。

状态分散以后，[[D05 推理服务与调度]] 需要在缓存亲和与排队之间选择：命中副本忙时，等待命中不一定优于在空闲副本重算。跨池传输还要经过 [[D10 通信与互联]]，并满足身份、版本和完成条件。研究结论最终应落在固定任务质量和流量下的首响应、生成节奏、有效吞吐和容量，而不只比较命中率。

## 投机执行：接受更多 token，可能把成本移到验证和协调

[[D07 投机执行与解码加速]] 用较便宜的工作提出候选，再让目标执行验证。收益要看每轮有效输出和总耗时，而不是单看接受率。候选的链/树、长度和验证布局会改变矩阵形状、Attention 掩码与 KV 分配，因而进入算子与编译域。

动态预算还可能改变图捕获与调优覆盖；起草、验证分离部署则增加通信与滞后反馈。放进服务以后，验证可能占用原本可服务其他请求的资源。低并发单请求的优势，需要重新检查高并发下的延迟和 goodput。

另一个连接是数学语义。保持目标分布的执行加速，与额外采样、搜索、验证器带来的质量—预算选择不同，后者见 [[D03 后训练与推理时计算]]。二者可以组合，但必须分别报告计算预算、输出语义和质量证据，不能混成同一种加速。

## 异步学习：调度顺序还会改变训练数据

生成、评分和更新重叠，可以减少空等，也会让样本来自不同策略版本。完成更快的任务若优先进入更新，还可能改变数据来源比例。因此 [[D03 后训练与推理时计算]] 的系统调度受到 [[D01 数据工程与训练配方]] 的约束。

训练和生成采用不同并行布局时，[[D02 分布式训练与模型状态]] 需要转换权重分片；发布新版本后，旧请求和旧状态怎样继续，又与 KV 身份、通信完成和 [[D16 工程交付与模型生命周期]] 相连。

2026-11-09 核验的两组证据把这条联系拆得更清楚。Reshard按目标所有权减少权重交接中的冗余传输，缩短的是同步的一部分；TitanRL则约束同权重在生成端与训练端怎样得到一致概率，处理的是数值路径。更快同步不会自动修好数值差异，位一致也不会让行为策略变新。后者的KV页面修复还说明：为数值契约选择的Attention路径，会反过来约束cache布局与依赖版本。二者须共同进入学习时间线，最终仍以独立任务质量和完整成本验收。[Reshard报告](https://developer.nvidia.com/blog/accelerating-reinforcement-learning-weight-refit-with-the-reshard-collective/) · [TitanRL限定契约](https://github.com/pytorch/torchtitan/blob/3da9eac83509091503e48534c9e3ca06b4d76fd7/torchtitan/rl/BITWISE_PARITY.md)

恢复也要说明终点：进程重新启动、状态载入、已提交更新和样本进度一致、完整学习质量维持，是不同承诺。提高 rollout 吞吐不能代替达到同等独立评估质量的总时间与成本。

## 检索与 Agent：进入模型之前和离开模型之后都还有工作

[[D15 检索推荐与在线数据系统]] 决定模型能看到哪些候选和上下文。召回、过滤与重排既改变质量，也改变后续输入长度，进而影响 prefill、KV 和服务排队。只提高检索 QPS，若减少了必要信息或增加下游工作，仍需按整项任务判断。

[[D14 多模态 Agent 与流式系统]] 还可能包含图像编码、音频块、视频去噪、工具与环境等待。阶段之间的信息和时间结构不同：某段流式输出提交后可能不能撤回，取消请求也不意味着所有物理访问已结束。

上游选择还发生在两个不同时间尺度。AgenticDS寻找训练候选池，改变模型有机会从哪些数据学习；Rerank 5选择文档内的证据片段，改变当前问题有机会读到哪些事实。前者需要训练效用验证，后者需要答案支持与输入预算验证，二者都不能只以相关性排名作为最终质量。片段选择还依赖API是否暴露相应输出，不能由同名模型可经平台调用推导功能可用。[AgenticDS v1](https://arxiv.org/html/2610.39608v1) · [Rerank接口边界](https://docs.cohere.com/docs/cohere-on-openrouter)

因此这里需要任务级追踪标识，将模型、检索、工具、编码、重试和状态版本关联起来。应用状态告诉我们事情做到哪了，物理缓存告诉运行时哪些计算可能复用；恢复任务要同时理解二者。

## 硬件与交付：能编译、能运行与值得部署仍有距离

[[D13 硬件与跨平台系统]] 改变计算、带宽、容量、同步和互联的比例。[[D09 编译 DSL 与自动优化]] 需要重新选择布局、代码与调优配置，低精度可能还要求新的质量验证。相同 API 和相同模型名字不能证明这些条件都保留。

编译或量化的最佳配置要绑定设备、版本、形状和测量条件。发布系统要把权重、处理器、适配器、编译制品和协议作为可追溯组合；滚动更新期间还要处理旧缓存、在途任务、回退和资源回收。注册标签变化不是物理服务已经一致切换的证据。

llm-d的单prefill升级问题与SGLang/NIXL取消问题，分别暴露“没有完整可服务版本”和“没有结束物理引用”两种失败。前者需要容量与滚动预算，后者需要回收协议；一项路由或传输功能无法同时代替两者。TorchTPU与CUDA13.5又把同样的问题带到硬件层：API、图通信、实际算术精度、驱动和preview库必须按组合核验。此处依据是选定固定版本与官方支持文档，尚未形成完整部署或故障验证。[llm-d故障](https://github.com/llm-d/llm-d/issues/2854) · [取消边界](https://github.com/llm-d/llm-d/blob/378b42d18dabe0b9c4ced4e6f3670d93b52db08e/docs/operations/disaggregation/sglang.md) · [TorchTPU固定通信条件](https://github.com/google-pytorch/torch_tpu/blob/680b8436e61baf6f832f32d2bc8ca55615ff619e/docs/distributed_support.md)

## 把一项优化代回完整决策，结论会怎样变化

### 状态更小以后，应该多接请求还是减少设备

固定层与head结构，状态载荷随保留位置数和位宽乘积增长。位置减半、位宽降为四分之一，理想载荷可变为八分之一；但前者改变参与计算的信息，后者改变数值误差，组合质量不能用容量乘法证明，scales、近期高精度区和临时量也尚未算入。D06的171 MiB算例加入了scale/zero-point和高精度残余，对齐、索引与临时workspace仍需另计；D08则说明消费者是否直接读取压缩状态，会改变GPU实际容量。

即使容量确实节约，服务策略仍有两种选择。保持卡数、多接序列，可能增加权重摊销，也会加长每轮计算和Attention读取；减少卡数、保持请求量，则会改变并行、路由和故障余量。前者不能只按更大的batch报好消息，后者不能只按每卡利用率报坏消息。D05要重新测同任务质量下的TTFT、输出间隔与goodput，D12要重新核准入与故障余量，D16要把新表示和kernel作为同一制品发布。

远端命中也有类似反馈。GPU重算变快后，过去划算的缓存层可能不再划算；有多个请求共享同一前缀，又可能摊薄一次取回。这说明缓存策略不是仅由存储成本决定，必须与当前模型、设备、共享引用和等待队列一起求解。网络慢时选择重算、队列拥塞时选择另一副本，都是合理的条件化结果。

### 训练吞吐提高以后，为什么到目标质量反而可能更慢

D01的数据过滤、重写和混合改变每个token包含的学习信号；D03的准入、超时与失败处理改变真正进入更新的轨迹集合。设某类难任务更慢，系统若只消费先完成者，吞吐可提高，但更新分布不再是原配方。直接丢全失败prompt，和仅不计算零优势样本的梯度，也未必有相同分母与后续采样行为。

因此不能先把D02的并行配置调到最高token/s，再假定学习目标自然维持。应保存数据/策略版本和已提交更新边界，确认全局batch、梯度归一化和轨迹权重，随后再看达到独立任务标准的总成本。清洗所用教师、生成与验证的GPU时间、失败重试和检查点恢复都要进入账目。系统与算法共同改变的实验可以证明完整方案在该条件下有效，却不能把全部质量差异归给某个调度器。

D12的弹性和迁移也处于这条链上：替换机器可以复用通讯关系与已热数据，仍需在一致更新边界接续；并行组变化后，状态重分片、数据游标和随机状态必须重新对应。若重放未提交区间，不能误判为重复应用已提交更新；若跳过慢轨迹，则必须说明学习语义已经改变。

### 检索更快以后，生成端可能面对更重的工作

D15把召回候选从少量扩大到大量，能给重排更多选择，但不会自动减少任务延迟。候选更多意味着向量/特征读取、模型交互和过滤工作更多；将更多文本送进生成，又增加prefill和KV。对多向量、视觉patch或长视频，局部表示数量还会进一步改变D08的归约和不规则访问。

此时可以在检索端花更多算力换更短、更相关的最终上下文，也可以将预算交给生成端处理更多证据。二者需要相同任务下比较答案支持、漏召回、重排、首响应与总成本。查询的embedding模型、索引与过滤可见版本要匹配，更新越频繁，D16的共同发布、D11的后台维护与D09的图/形状覆盖越重要。

多模态和Agent又增加不可随意重算的边界。音频已播放、工具已写入外部系统，回退模型版本不能撤销它们；仅缓存失效重算则通常可以。这也是为什么应用提交、模型状态、设备访问完成和制品版本必须分别记录，再在同一次任务里对齐。

## 每个跨域结论怎样验收

| 需要固定或记录的对象 | 为了排除什么误判 |
| --- | --- |
| 模型/任务质量、输出语义、输入与到达分布 | 用更容易或不同的工作冒充实现进步 |
| 硬件、软件、后端、实际 dispatch 与制品版本 | 把不同能力拼成一个未存在的组合 |
| FLOPs、各层级流量、状态峰值、排队与关键依赖 | 只看到局部省下的成本，漏掉转移到别处的成本 |
| 正确性/数值/长期质量与故障验证 | 用单元测试、短曲线或正常路径代替完整承诺 |
| 测量边界、编译/调优、预处理、失败与重试分母 | 比较不同范围，或只保留成功与最好一次 |
| 资源、成本、能耗与可恢复性 | 高利用率或更快 kernel 没有兑现为有效产出 |

作者报告、原型代码、正式版本与独立复现分别说明。当前各域的待核问题构成下一轮研究输入；发现新的依赖或路线时也可以改变地图，不要求把所有技术强行归进既有 16 个域。
