# Lecture 10：Incorporating Tools

> [!abstract] 本讲一句话
> 工具把语言模型从“生成答案”扩展到“生成可执行调用、接收真实观察、继续推断”；可靠性取决于调用选择、接口约束、执行隔离与失败恢复，而不只取决于模型能否生成一段正确 JSON。

## 1. 什么才算语言模型的工具

课堂给出的定义有三个要点：工具位于 LM 之外、属于模型所处环境、通过具有输入参数和输出的功能接口调用。

这一定义把“模型知道怎么算”和“模型可调用计算器”分开了。
前者是参数内部的预测能力；后者是将部分任务交给外部程序执行。
模型生成 `calculator(123 * 456)` 只生成了调用描述，计算结果要由外部执行器产生。

工具不一定是远程 API。
本地 Python interpreter、文件读取函数、浏览器控制器都满足这个抽象。
工具后面也可以是另一个模型，例如视觉问答或机器翻译系统。

因此，判断标准不是“有没有联网”，而是有没有一个外部可执行接口，以及接口是否把观察结果或环境变化交还给系统。

## 2. 三类工具：观察、行动与计算

| 类别 | 对模型增加什么 | 课堂例子 | 核心系统问题 |
| --- | --- | --- | --- |
| Perception | 参数中没有的环境信息 | 搜索、读文件、数据库查询、天气 | 新鲜度、相关性、返回量 |
| Action | 改变外部环境的能力 | 编辑文件、操作应用、播放音乐 | 权限、副作用、可恢复性 |
| Computation | 更可靠或高效的运算 | 计算器、Python | 执行正确性、资源限制 |

三类不是绝对互斥的 API 标签。
同一个工具可以先读数据、再计算、再写结果。
分类的用途是分析它究竟给系统带来了哪种能力，以及失败后会产生哪种后果。

例如“查询日历事件”主要是 perception，“新增日历事件”是 action。
即使它们属于同一服务，也不能因为模型已经获准读取日历，就默认它获准修改日历。
这是根据课堂分类得到的工程延伸，而不是一个 API schema 自动提供的保证。

工具还可以跨模态：文本模型调用图像问答、视频转录或音乐播放接口。
接口使模型无需直接拥有所有感知、计算和执行能力。

## 3. 工具调用是一次控制权交接

课堂的基本流程可以写成：

```text
用户问题 + 当前上下文 + 工具说明
             ↓
LM 生成工具名和参数
             ↓
应用解析、校验并执行
             ↓
工具返回 observation
             ↓
observation 加入上下文，LM 继续生成
```

这一循环包含两个不同的概率来源：

$$
a_t\sim\pi_\theta(a\mid h_t),\qquad
o_{t+1}\sim P_{\rm env}(o\mid a_t,s_t).
$$

这里 $h_t$ 是模型可见历史，$a_t$ 是调用，$s_t$ 是环境状态，$o_{t+1}$ 是实际观察。
公式是本文整理，用来强调工具结果不是 LM 自己“续写”出来的结果。
确定性计算器的环境分布可以退化为一个固定结果；网络 API 则可能超时、返回变化的数据或错误。

早期 Siri/Alexa 系统常把任务拆成 intent classification 与 slot filling。
现代 LM 可以直接从自然语言生成函数调用，但功能上仍然要解决“调用什么”和“参数是什么”。
生成式建模改变了接口生成方式，没有消除语义解析问题。

## 4. WebGPT：模型控制检索过程

### 4.1 为什么给 LM 一个浏览器

参数知识可能过时，也无法为每一个回答提供可追溯来源。
WebGPT 使用文本浏览环境，让模型执行搜索、打开链接、滚动、摘取引用，再形成答案。
课堂把它作为现代大模型工具使用的早期代表。

这里的重要变化是：模型能根据已读内容决定下一步要查什么。
一次查询没找到足够证据，可以继续查询；信息相互冲突，可以追加阅读。
检索成为推理过程中的动作。

### 4.2 示范数据与偏好数据承担不同工作

课堂概括了两种监督：

1. 人类使用相同浏览界面完成任务，记录动作轨迹，用来做行为克隆。
2. 对候选回答收集人类两两偏好，训练 reward model，用于进一步优化或选择。

行为克隆教“怎样在环境中操作”；偏好数据教“什么样的最终回答更好”。
拥有浏览器不意味着自动学会高质量检索策略，仍需要数据或足够强的基础模型。

> [!note] 原论文补充
> [WebGPT 原论文](https://arxiv.org/abs/2112.09332)研究了人类反馈优化；其摘要报告的最佳设置是 GPT-3 行为克隆加 reward-model rejection sampling。不能把课堂对 RLHF 的概述理解成“论文最佳模型必然来自 RL”。

### 4.3 与 RAG 的关系

课堂提问针对的是最常见的固定 RAG 流程：

```text
query → 一次检索 → 检索结果拼入 prompt → answer
```

WebGPT 风格的过程则允许 LM 自主调用检索和浏览工具。
两者不是互斥技术：agentic retrieval 也可以属于广义 RAG。
应区分的是“检索计划是否由固定 pipeline 决定”，而不是争论是否使用 RAG 这个名字。

引用也不是正确性的充分条件。
它让人可以核查证据是否存在、证据是否真正支持答案；模型仍可能误读页面或选择不可靠来源。

## 5. Toolformer：从预测收益构造工具监督

### 5.1 训练数据从哪里来

Toolformer 不依赖大规模人工逐条标注“这里应该调用计算器”。
课堂以 Pittsburgh 被称为 Steel City 为例，说明以下流程：

1. 从普通 LM 文本开始。
2. 根据少量工具示范，采样可能有帮助的调用位置、工具与参数。
3. 真实执行候选调用。
4. 比较加入结果前后，对后续原文的预测损失。
5. 保留有帮助的调用，再微调 LM。

这相当于把已有文本的后续 token 当作一个自监督评价目标。
工具调用的价值由“它是否帮助预测这段原文”定义。

### 5.2 简化损失与正式过滤条件

为理解课堂，先用简化写法：

$$
\Delta L=L_{\rm without\ result}-L_{\rm with\ result}.
$$

当 $\Delta L$ 足够大，说明工具结果改善了预测。
但原论文的负基线更仔细：既比较“没有调用”，也比较“只有调用文本但没有结果”。

$$
L_i^- = \min\{L_i(\varnothing),L_i(e(c_i,\varnothing))\},
\qquad L_i^+=L_i(e(c_i,r_i)),
$$

$$
\text{保留调用}\iff L_i^- - L_i^+\ge\tau_f.
$$

$c_i$ 是调用，$r_i$ 是返回值，$e$ 是把调用编码成文本的方法。
这样可避免仅仅因为“把问题换一种说法写进上下文”就把一个没用的工具结果算作贡献。
具体定义与五种工具列表见 [Toolformer 第 2–3 节](https://arxiv.org/html/2302.04761)。

### 5.3 预测帮助不等于事实保证

学生在 [15:29](https://www.youtube.com/watch?v=prcsOlxc4vo&t=929s) 指出：提高正确续文的概率，不一定意味着工具返回本身完全正确。
讲师认可，方法筛选的是“对模型有帮助”的调用。

需要分开三个量：

- 工具输出是否正确；
- LM 使用输出后，原文 loss 是否下降；
- 最终任务是否成功。

这三个指标可以相关，但不等价。
训练代理指标的优化，不能直接充当端到端正确性的证明。

### 5.4 规模结果与局限

课堂指出，小模型可能连合理调用都生成不好，因此工具收益在一定模型规模内随能力增强而增加。
但讲师也明确把“更大模型可能自身已能解决任务，工具相对收益下降”作为推测。
不能把课堂曲线外推成工具收益随参数量无限增长。

Toolformer 的固定工具箱与后面的动态 API 检索也不同。
学会五类固定工具，不等于可以对成千上万份未知 API 文档都正确调用。

## 6. Function calling：让工具描述变成可校验接口

### 6.1 Schema 描述的是允许生成的形状

课堂天气工具包含名称、描述、参数类型、城市、温度单位和必填字段。
最小示意为：

```json
{
  "name": "get_weather",
  "description": "Get current weather for a location",
  "parameters": {
    "type": "object",
    "properties": {
      "location": {"type": "string"},
      "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
    },
    "required": ["location"]
  }
}
```

本文示意省略具体供应商封装，不作为某个当前 API 版本的调用样板。
Schema 帮助完成一致解析、类型检查和参数约束。
模型仍可能选择错城市、错工具、错单位，或在不该调用时调用。

### 6.2 谁真的执行函数

课堂学生问：LM 返回的只是文本，为什么不直接调用函数？
关键是用户提供自然语言请求，通常没有提供已经解析好的工具名与参数。
LM 承担从自然语言到结构化调用的转换；应用承担实际执行。

模型输出 `get_weather(location="Boston")` 不代表 Boston 的天气已查到。
应用必须取出调用，执行对应程序，把结果以正确的 call ID/消息关联交回。
否则模型看到的只是自己的计划，而不是外部证据。

### 6.3 格式可靠性与语义可靠性

课堂讨论了代码嵌入 JSON 时的引号、反斜杠与缩进转义。
格式训练和约束解码可以降低解析错误，但不能证明代码含义正确。

工程上可以分别统计：

$$
P(\text{成功})=
P(\text{格式有效})\,
P(\text{语义正确}\mid\text{格式有效})\,
P(\text{执行成功}\mid\text{前两者}).
$$

这是条件概率链式分解的示意，不要求各事件独立。
把格式分数当作任务成功率，会漏掉后面两层失败。

## 7. 并行调用与程序组合

并行 function calling 允许一轮 LM 输出多个调用，例如同时查询 Boston 与 New York 天气。
它减少的是模型往返次数，实际并行仍由应用调度。

若两个调用互相独立：

$$
T_{\rm serial}\approx T_1+T_2,
\qquad
T_{\rm parallel}\approx\max(T_1,T_2)+T_{\rm overhead}.
$$

但“先搜索城市列表，再查询这些城市天气”具有数据依赖，不能提前生成未知参数。
存在副作用的调用还可能发生写冲突，不能只因一轮返回了两个调用就无条件并发。
这些是把课堂并行概念落到运行时需要补上的边界。

并行调用也不直接提供 `if`、`for`、聚合与中间变量。
这些正是下一步“在程序中组合工具”的价值。

## 8. MCP：工具发现与调用的协议层

### 8.1 Host、client、server 的分工

课堂用 filesystem server 举例：一个 server 可以同时暴露列文件、读文件、改文件等多个工具。
AI application 作为 host，通过 client 连接一个或多个 server。
server 把底层 API 或本地能力包装为可发现、可调用的接口。

从课堂抽象看，server 至少承担：

1. 返回它提供哪些工具，以及工具的参数说明。
2. 接收调用、运行对应逻辑、返回结果。

模型本身不需要凭空知道某个 server 的工具。
应用取得描述后，把允许使用的工具提供给模型。

### 8.2 协议与权限不是同一个概念

讲师用“把 API key 藏在 middleware 后面”解释 MCP 的一个实际好处。
准确的工程理解是：凭据可以留在应用或服务端，由运行时管理，不必进入语言模型上下文。
这不是 MCP 独有能力，也不意味着使用 MCP 就自动解决授权、最小权限或恶意工具输出。

工具协议回答“怎样发现并调用能力”；权限系统回答“这次任务允许调用哪些能力、允许作用于哪些资源”。
两者需要配合。
本讲不应被理解成 MCP 安全规范的完整介绍。

### 8.3 FastMCP 与 A2A

课堂展示用装饰器把 Python 函数暴露成 MCP 工具，强调开发门槛可以很低。
工具描述依然需要说明参数含义、输出结构和失败情形。
“容易包装接口”不等于“模型总会理解接口”。

对 A2A 的简短问答指出：MCP 常用于 agent 与工具通信，A2A 面向 agent 与 agent 通信。
工具后面也可以是 agent，因此不能只按模型数量判断协议层次。
本段只是课堂定位，没有展开后续协议细节。

## 9. PAL：把运算交给解释器

PAL 让 LM 生成程序，把自然语言推理与 Python 运算结合。
对于数学问题，LM 负责把题意映射成变量、关系和程序；解释器负责执行算术。

以下是本文构造的同类示例：

```python
# 三盒，每盒 12 支，送出 7 支
boxes = 3
per_box = 12
given_away = 7
answer = boxes * per_box - given_away
```

直接 CoT 可能在 `3 * 12 - 7` 的运算中出错；PAL 能把该运算交给确定性执行器。
但若 LM 把“送出 7 支”翻译成 `+ 7`，解释器会忠实执行错误程序。
PAL 降低的是一部分执行错误，无法自动消除题意建模错误。

官方课件的 PAL 表格给出以下 solve rate，三行均标注 Codex：

| 方法 | GSM8K | SVAMP | ASDIV | MAWPS-SingleEq | MAWPS-AddSub |
| --- | --- | --- | --- | --- | --- |
| Direct | 19.7 | 17.1 | 4.1 | 58.8 | 72.0 |
| CoT | 65.6 | 74.8 | 56.9 | 79.0 | 86.0 |
| PAL | 72.0 | 79.4 | 76.9 | 79.6 | 92.5 |

这说明在该表设置下，程序执行在多个数据集上改善了结果，但改善幅度并不一致。
课件正文写 GSM8K 上有“15% absolute improvement”，与同页 $72.0-65.6=6.4$ 个百分点矛盾；此处按表格保留 6.4 个百分点，不沿用该文字结论。
正式实验配置仍应回到 [PAL 论文](https://arxiv.org/abs/2211.10435)检查模型、提示与数据集，不把历史结果当成所有模型的保证。

## 10. 代码执行需要真正的隔离边界

### 10.1 课堂列举的风险

模型可能误删工作、安装有问题的依赖，或者把网页中的恶意内容当作行动指令。
即使用户只要求完成正常任务，执行过程也可能进入危险状态。
因此风险并不只来自用户输入，也来自工具返回、依赖和模型自身的误操作。

### 10.2 三类执行环境

| 方法 | 课堂解释 | 适合建立的直觉 | 不能假设的保证 |
| --- | --- | --- | --- |
| 本地受限解释器 | 限制 import、模块、危险操作 | 易接入、开销小 | 同进程过滤不是坚固安全边界 |
| Container | 将执行放到隔离运行环境 | 可配置文件、网络、资源约束 | 容器共享内核，配置仍决定隔离强度 |
| WebAssembly | 在受限运行时执行 | 可限制宿主能力，适合部分浏览器场景 | 仍需检查暴露的 host functions |

课堂强调：阻止所有危险 Python 写法非常困难，同进程执行还可接触进程内存。
仅搜索 `os`、`subprocess` 或双下划线不是完整的安全方案。
本节对 container 的限定是工程澄清：不要把课堂概述理解成容器天然提供虚拟机级别隔离。

### 10.3 沙箱还属于 inference 成本

启动环境、安装依赖、复制文件和执行超时会进入任务总延迟。
复用沙箱可以降低启动成本，但要处理会话状态污染与用户隔离。
一次错误重试可能重新触发环境初始化，端到端成本不只是 token 费用。

## 11. Gorilla：从固定工具箱到 API 检索

当 API 数量变大，把所有文档塞入 prompt 会增加输入成本并干扰选择。
课堂介绍 Gorilla 的两个阶段：

1. 从 API 文档出发，用 self-instruct 生成“什么用户请求会需要该 API”的训练对。
2. 推理时检索候选 API 文档，再让模型生成调用。

合成 instruction 是由已知 API 生成的，所以天然知道相关 API 标签。
它可用于训练 instruction/API 文档匹配的 retriever。
这不是每次调用时“让 LM 自己猜存在什么函数”。

课堂同时指出原始 Gorilla 数据来自 Torch、TensorFlow、Hugging Face 等机器学习 API。
因此，不能仅凭“有很多 API”就把原始实验理解成覆盖所有企业业务场景。
Berkeley Function Calling Leaderboard 被介绍为工具调用评价入口；排名属于特定时间和测试集，本文不转载当期模型排名。

## 12. Reasoning for tool use 与 tool use for reasoning

### 12.1 让模型更会选择和构造调用

课堂的 RL 示例同时考虑 format reward 与 correctness reward。
格式可用 schema 验证；正确性拆成工具名、参数名、参数值等部分匹配，并处罚多余调用。
密集的部分分数给模型提供“接近正确”的学习信号。

可以用如下抽象表达，而不冒充原 slide 的具体公式：

$$
r = r_{\rm format}+r_{\rm tool}+r_{\rm parameter}
   +r_{\rm value}-\lambda r_{\rm excess}.
$$

当各项都是 gold call 的匹配指标时，它优化的是“生成预期调用”的能力。
若同一任务有多个等价工具或合法流程，基于固定 gold call 的分数可能处罚合理替代路径。
这是设计奖励时需要补充端到端验证的原因。

### 12.2 让工具帮助完成更复杂推理

反方向是在 reasoning model 的 rollout 中接入代码解释器，再以最终任务结果作为训练信号。
模型可以学到何时值得计算、怎样把结果纳入后续推理。
区别在于评价对象：一边主要评调用本身，一边主要评借助工具后完成的任务。

课堂提到某些实验 cold start 优于先做 SFT 的设置。
这里 cold start 指任务 RL 前没有该阶段 SFT，不是从随机权重训练整个语言模型。
讲师没有展开因果分析，因此不应把这一实验观察写成普遍训练处方。

## 13. 工具坏了，模型能否知道并恢复

课堂的失败评价分成两个层次：

- Awareness：是否识别工具不可用、输出异常或信息不足。
- Recovery/task success：识别后能否改用替代方案，并完成任务。

两者不等价。
模型可能正确说“这个接口不可用”，却仍反复调用；也可能知道失败但没有足够替代能力。
一次正确的错误说明不应被计作任务成功。

[FAIL-TALMS](https://arxiv.org/abs/2503.14227)还包含用户请求信息不足的情形；课堂主要展开了工具不可用的部分。
应记录失败类型、是否有可替代工具、是否请求必要信息、是否真的恢复。
在没有失败注入的理想工具环境中测出的调用准确率，无法覆盖这些行为。

## 14. TroVE：工具箱可以在测试时增长

课堂介绍的过程以已有 primitive functions 为起点。
每个任务尝试三种策略：使用已有工具、创建新工具、不使用额外工具。
例子中每种策略采样 $K=5$ 次，合计 15 条候选轨迹。

再通过 self-consistency 聚合答案，寻找更稳定有用的解法，把适合复用的函数加入工具箱。
长期很少使用的工具会被剪除，避免工具箱只增不减。

这里工具是可以保存和调用的程序，不是模型参数里不可见的记忆。
因此推理时可累积新能力，而无需每次更新模型权重。

需要留意 self-consistency 的边界：多数答案是伪标签，并不保证真实正确。
一个工具反复生成一致错误，也可能显得“很稳定”。
本文把持久化测试、接口版本和回归测试视为工程延伸，不把它们冒充课堂已经实现的每个步骤。

## 15. 课堂问答中值得记住的判断

**工具结果提高概率，就证明它正确了吗？**
没有。Toolformer 筛选的是预测帮助，课堂明确接受这一局限。

**为什么不用应用直接调用 API？**
应用仍负责执行；LM 的贡献是从自然语言和当前状态选择 API 并填参数。
当工作流与参数都已知时，直接写程序当然可以更简单。

**接入新 MCP server 后必须重写全部 prompt 吗？**
讲师认为足够强的工具模型常能依据描述使用新工具；但工具检索、权限和执行接入仍是应用的工作。

**多个工具都能完成任务，模型会自动选最优吗？**
课堂回答较谨慎：不一定擅长，需要明确选择策略或训练。
“优”也必须定义，是更准、更便宜、更快，还是副作用更小。

**多给一些重复工具是否更保险？**
讲师建议避免大量重复工具，因为描述消耗 context，还会干扰选择。
目标是提供任务需要的能力，而不是最大化工具数量。

## 16. AI Infra：把工具循环当作完整请求来测量

以下是由课堂内容推导的运行时视角：

$$
T_{\rm task}\approx\sum_t
\left(T_{\rm LM,t}+T_{\rm dispatch,t}+T_{\rm tool,t}
+T_{\rm observation,t}\right).
$$

其中 observation 不只包含传输，还包含序列化、截断、检索、下一轮 prefill。
一个工具返回十万行文本，可能使很快的 API 变成很慢的 agent 步骤。
应尽量在外部程序完成过滤与聚合，只返回当前决策需要的结果。

建议同时观察四类信号：

- 正确性：格式有效率、工具/参数选择、端到端成功率。
- 成本：调用次数、输入输出 token、工具费用、执行环境成本。
- 延迟：LM 时间、工具等待、失败重试、最长依赖链。
- 恢复：失败识别率、替代工具成功率、重复无效调用次数。

对有副作用的动作，记录调用 ID、目标资源、执行状态与返回证据。
网络超时可能意味着“没执行”，也可能意味着“已执行但响应丢失”。
两种情况不能用同样的无条件重试逻辑处理。

## 17. 自测与面试回答

### 1）工具为什么能增强 LM，而不一定需要增大参数量？

**回答：** 工具可引入参数外的新信息、确定性计算和环境操作能力。LM 负责选择与组合这些能力，因此系统能力可以超过模型内部已有的知识和运算能力。但调用语义与结果使用仍可能错误，不能把工具的局部准确率直接当作系统准确率。

### 2）Toolformer 如何不依赖大规模人工调用标注？

**回答：** 它用少量示范生成候选调用，真实执行后，用加入结果是否降低后续原文预测 loss 来筛选，再在增强文本上微调。原论文还把“只有调用文本但没有结果”作为基线，确保结果本身有贡献。筛选目标是预测帮助，不是外部事实验证。

### 3）Function calling 与执行工具是什么关系？

**回答：** Function calling 是模型输出结构化工具名和参数的接口。宿主应用负责验证、权限判断、调度、执行，并把真实结果与调用对应返回。没有执行结果，模型生成的调用只是动作建议，不能声称任务已经完成。

### 4）JSON Schema 能保证调用正确吗？

**回答：** 只能覆盖类型、字段、枚举等形式约束。合法 JSON 仍可能引用错误城市或文件、选择错误工具，或者在错误时机修改环境。评价要分别测格式、语义、执行与最终任务结果。

### 5）MCP 为什么不是另一个工具模型？

**回答：** MCP 是应用连接外部能力的协议层，server 提供工具发现和执行等接口，模型看到的是应用提供的工具说明。模型可以更换，底层工具也可以更换。凭据管理与权限可以在协议周围实现，但不能因使用 MCP 就默认安全。

### 6）并行 function calling 和 CodeAct 式程序组合有什么差别？

**回答：** 前者让一轮模型返回多个可独立执行的调用；后者用程序表达循环、条件、依赖和聚合。并行适合独立请求，程序适合复杂控制流。程序批量执行能减少 LM 往返，但大程序出错时定位和恢复也更复杂。

### 7）PAL 解决了什么错误，没有解决什么错误？

**回答：** PAL 把运算交给解释器，降低自然语言算术和机械执行错误。它仍由 LM 建模题意与生成程序，因此变量含义、单位、逻辑关系和目标函数都可能写错。执行成功只证明程序跑完，不证明程序表达了正确任务。

### 8）为什么同进程 Python 过滤不能代替真正沙箱？

**回答：** Python 有复杂对象与反射能力，枚举危险 token 很难覆盖所有路径，而且同进程共享内存与宿主权限。实际系统需要按风险配置进程、容器或其他隔离运行时，并限制文件、网络和资源。过滤规则只能是辅助措施。

### 9）工具失败的 awareness 为什么不足以证明鲁棒性？

**回答：** 它只说明模型识别了故障。鲁棒系统还要采取有效下一步，例如换工具、修正参数、请求缺失信息或明确无法继续，并避免重复无效调用。评价必须把失败识别和任务恢复分开统计。

### 10）TroVE 的推理时学习与权重微调有什么区别？

**回答：** TroVE 通过生成、复用、剪除程序函数改变外部工具箱，不必更新 LM 权重。它可以积累可检查的任务能力，但多数投票只是代理监督；工具库仍需防止错误累积、接口冲突和无用增长。

### 11）工具越多为什么可能越差？

**回答：** 每份工具说明占用输入 token；语义相近的接口会增加选择歧义。规模变大后可先检索相关工具，再提供清楚的选择策略。应按端到端成功率与成本评价工具箱，而不是按工具数评价。

### 12）怎样比较“多调用一次工具”和“多想一些 token”？

**回答：** 先识别瓶颈：缺外部事实时内部思考不能创造证据；机械计算时解释器通常更可靠；已经拥有信息但不会组合时额外推理可能有帮助。再测相同任务分布下的准确率、延迟、成本和失败风险，而不是只比较模型 token 数。
